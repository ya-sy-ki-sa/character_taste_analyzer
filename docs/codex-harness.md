# GPT-6 Astra向けCodex開発ハーネス

このリポジトリで、既存のCodexを使って「調査 → 実装 → 検証 → 結果報告」を進めるための最小構成です。VS Codeでの対話を入口とし、単一エージェントで運用します。

## 構成と前提

| 要素 | 役割 |
| --- | --- |
| [プロジェクト設定](../.codex/config.toml) | `gpt-6-astra` と推論強度 `high` を指定 |
| [作業指示](../AGENTS.md) | 正本の探索、作業範囲、Skill、検証、報告の共通ルール |
| [品質評価](quality.md) | 既存のテストとCI共通の `npm run verify` |

導入計画時の確認環境はCodex CLI `0.153.0`、Node.js `24.20.0`、npm `11.19.0`です。CodexはVS Code拡張に同梱された実行ファイルを利用できます。認証と権限は既存環境から引き継ぎ、ユーザー共通設定やAPIキーをこのリポジトリへコピーしません。

この設定は開発を担当するCodex向けです。アプリのLLMモデル割当、公開API、型、DBには変更を加えません。SDK、MCP、プラグイン、CLIラッパー、自動デプロイは追加しません。非同期ツール呼び出しや途中指示はCodexが提供する範囲で利用し、APIの実行ループを自作しません。

## 起動と設定の確認

1. VS Codeでリポジトリのルートを開きます。端末で `codex --version`、`node --version`、`npm --version` を確認します。`codex` が見つからない場合は、インストール済みCodex拡張の実行ファイルを確認します。
2. リポジトリがCodexで信頼済みであることを確認します。プロジェクト設定は信頼済みの場合に読み込まれます。認証・信頼状態の診断には、ルートから `codex doctor --summary` を実行します。
3. 設定の厳密な診断には `codex --strict-config doctor --summary` を実行します。ユーザー共通設定が原因のエラーも区別して確認し、別プロジェクトに影響する設定を自動で変更しません。
4. Codexの新規会話を開始します。モデル選択表示でGPT-6 Astra、推論強度でhighを確認します。既存会話の選択や明示的な起動オプションが優先される場合は、プロジェクトの既定値と区別します。
5. 最初に次の読み取り依頼を送信します。モデルの自己申告だけで設定適用を判定せず、設定表示と実際の回答を併せて確認します。

```text
ファイルを変更せず、このリポジトリの作業指示の出典、構成の正本、
文書変更とコード変更それぞれの検証手順を説明してください。
```

端末で対話する場合は、リポジトリのルートから `codex --strict-config` を起動します。モデルの引数を付けず、プロジェクトの既定値が適用されることを確認します。読み込まれる指示の調査には `codex debug prompt-input` も利用できます。出力にはユーザー共通の指示や環境情報が含まれ得るため、そのまま共有文書へ転載しません。

`AGENTS.md` や設定を更新した後は、新規セッションで再確認します。未認証、利用権限不足、Astraを利用できない状態は、設定が正しいことと分けて報告します。別モデルへの自動切替は行いません。

## 依頼テンプレートと標準フロー

```text
目的:
期待する挙動:
制約:
完了条件:
```

例えば「登録フォームの入力エラーを修正する」という目的に対し、期待する挙動には再現操作と修正後の表示、制約には通常版・dark版の対象、完了条件には確認するテストや画面を記載します。計画だけ、読み取りだけの場合も制約へ明記します。

Codexは既存差分と関連する正本を確認し、実装、対象検証、必要な品質ゲート、最終差分の確認まで進めます。重要な不明点を質問している間も、回答に依存しない調査は続けます。不要な承認や成功済みの全検証の反復は挟みません。

| 変更・状況 | 検証と完了条件 |
| --- | --- |
| 文書のみ | リンク先、記載したコマンド、差分を確認。アプリ全体のテストは不要 |
| Codex設定 | TOMLの構文、厳密な設定診断、新規セッションでの適用を確認 |
| コード | 関連テストと `npm run typecheck` を実行し、引き渡し前に `npm run verify` を1回通す |
| UI | コードの検証に加え、対応Skillの画面基準とPlaywrightの結果を確認 |
| 検証失敗 | 原因を調べて修正し、必要な検証を再実行。未解決なら完了条件未達として報告 |

起動は[導入・運用](operations.md)に従い、アプリの実LLM呼び出しが不要な確認には `npm run dev:offline` を使います。E2Eは既存の専用ポートと一時D1を使い、開発用DBや既存サーバーを再利用しません。環境不足によるWebKitのスキップなどは明記します。Fake／Replayの成功を実LLMの精度向上の証拠にはしません。

最終報告には変更内容、実行コマンドと結果、未解決事項を残します。長いコマンド出力の転載は不要です。

## 中断・再開と途中の要件修正

中断前には次の内容を会話に残します。

```text
目的:
変更済み箇所:
検証結果（未実行も明記）:
残作業:
追加された制約:
```

再開時は引き継ぎと現在の `git status --short`・関連差分を照合します。過去の検証後に変更があれば必要な検証をやり直します。途中の追加指示は元の目的へ取り込みます。新しい会話では、元の会話の記憶を前提とせず、この引き継ぎを渡します。

モデル利用不可、設定不整合、検証環境不足では、実際のエラー、完了した部分、残作業を区別して報告します。設定ファイルを置いただけでは、Astraの利用や検証の成功を保証しません。

## 導入時の対話確認

次の3ケースを新規セッションで確認します。文書修正の試行にはGit管理対象外の `.artifacts/codex-harness/` に置く確認用文書を使い、変更対象を明示します。

| ケース | 操作 | 合格条件 |
| --- | --- | --- |
| 読み取り調査 | 起動手順の読み取り依頼を送る | 指示の出典と正本を説明でき、作業ツリーの差分が増えない |
| 小さな文書修正 | 確認用文書の指定した1行だけを修正するよう依頼する | 対象行だけが変わり、不要な承認・アプリ全体のテストなしで結果を報告する |
| 途中の要件修正 | 確認用文書の追記を依頼し、作業中に「既存本文を保持し、追記は1文にする」と追加する | 元の追記目的と新しい制約を満たし、残作業を見失わない |

設定値、指示の読み込み、対話中の挙動は別々に確認します。途中指示が実行終了後に届いた場合は、継続ターンの確認として記録し、作業中の取り込み成功とは数えません。結果には確認日、Codexバージョン、実施したケース、未実施の理由を残します。検証用の記録・文書は `.artifacts/codex-harness/` に保存し、Gitには追加しません。
