# プロンプト記述方針

アプリ内のLLM呼出は、システムからデータを受け取り、構造化した結果をシステムへ返す処理です。固定指示は対話的な依頼文ではなく、処理仕様として記述します。正本は [worker/llm/prompts](../worker/llm/prompts) と、外部出典参照を所有する [provenance/registry.ts](../worker/platform/provenance/registry.ts) です。

## 記述形式

処理に必要な節だけを使用します。短い修復指示に不要な節を増やさず、複合プロンプトでは責務の異なる節を組み合わせます。

| 節 | 内容 |
| --- | --- |
| TASK | 処理目的と対象 |
| INPUT_CONTRACT・INPUT_MAPPING | 入力の役割、出所、根拠として使える範囲 |
| DEFINITIONS | 判断に必要な用語の作業定義 |
| PROCEDURE・DECISION_RULES | 判断順序、条件と結果 |
| PRIORITY・INVARIANTS | 競合時の優先順位、保持する意味、禁止する変換 |
| OUTPUT_CONTRACT・OUTPUT_MAPPING・REFERENCE_RULES | 出力項目の意味、項目間の整合、参照先 |
| UNRESOLVED | 不確実・不整合・根拠不足の場合の出力 |
| DOMAIN・AUDIT_SCOPE等 | 版または処理固有の適用範囲 |
| BOUNDARY_EXAMPLES | 同じ規則でも判断が分かれる具体例 |

「〜する」「〜しない」と条件分岐を用い、一つの規則に複数の責務を混在させません。専門用語や記号を増やすこと自体を目的にしません。出力の構造・型・許可値は共有Schemaを正本とし、プロンプトは意味判断と項目間の整合を中心に定義します。仕様中の用語や節名を出力フィールドとして追加しません。

## 専門概念の適用

| 適用先 | 概念 | 判断への対応 |
| --- | --- | --- |
| 属性命名・仮説 | 記号媒体、文脈上の意味、意味作用 | 具体的な表現、その意味、両者の結びつきのどれが評価対象かを区別 |
| 嗜好抽出・意味監査 | 命題、否定の作用域 | 対象の否定、評価の否定、反応の否定を区別 |
| 文脈抽出・意味監査 | 意味役割、照応 | 行為者・対象・経験者・所有者と代名詞の参照先を保持 |
| dark版の理解 | 主体性、Ontology、状態差分 | 意思と外部支配、許可された概念体系、基準状態からの変化を区別 |
| 生成・検査 | ハード制約、ソフト制約 | 必須・禁止と希望を区別し、優先順位と未達時の扱いを固定 |

記号論の導入は、表現・対象・解釈の関係を扱う[パースの記号の定義（原文集）](https://cspeirce.com/rsources/76defs/76defs.htm)を参照した、このプロジェクト向けの応用です。学説全体を実装したものではありません。「記号媒体」「文脈上の意味」「意味作用」はプロンプト内で適用範囲を定義し、ユーザーの好悪や反応経路を学説上の概念と一対一に同一視しません。

意味の存在と、その意味への好意は別々の根拠を必要とします。黒色から悪、首輪から従属、面影の残存から自我の保持を自動推定しません。通常版では形や色そのものへの評価を保持します。dark版ではダーク文脈との結びつきを必要とします。仮説提案では、確認済み人物理解に根拠がある未確認の好みを提案でき、抽出とは確定の条件が異なります。

属性名は比較可能で分かりやすい日本語を使います。意味の保持を短文化より優先し、専門概念に合わせて入力の意味を拡張・削除しません。原文引用、主体、条件、否定、明示と推測の区別を保持します。

## 変更と検証

人物理解、通常版・dark版の嗜好、仮説、生成・検査、意味監査、補完、修復、比較、外部出典参照に適用します。処理の組み立てと呼出回数、出力Schema、辞書、集計式、既存データはこの記述変更では変えません。版・処理固有の規則を別処理へ混入させません。

記述形式の変更とは別に、[解析の判定境界と補完処理の改修](analysis-reliability-plan.md)で、通常版の反応定義の共有と、根拠検証後の補完判定を追加します。補完の上限は各stageで1回のまま、監査では十分に見えても検証後に不足した場合を対象に含めます。

本文を変更したプロンプト・方針はバージョンを更新し、`npm run assets:generate` で [manifest](../contracts/generated/prompts.json) を再生成します。現在のバージョンとハッシュはmanifestを参照します。既存の構成境界・保存・パイプラインテストと `npm run verify` で契約の整合を検証します。

Fake・Replayの通過は意味解析の改善実証ではありません。実LLM評価を明示的に依頼された場合に、[属性評価例](preference-attribute-evaluation.md)と既存の評価資料を同じモデル・入力条件で比較します。対象の保持、分割の適切さ、否定・主体・条件、象徴的意味の過剰推論、明示内容の取りこぼしを確認し、別出力先へ保存します。
