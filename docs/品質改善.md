# 分析・生成の品質改善

2026-09-05。分析・生成の現行処理を記載する。旧契約の読み替えやデータ補完は行わない。

## 実装した流れ

- 分析は、確認済みの属性・根拠・適用範囲・明示性・confidence・カスタム差分を読み戻す。カスタム登録では原典像ではなく対象のrepresentationを選ぶ。訂正は原資料に優先し、削除・差し替えも監査へ渡す。確認時の訂正とその出典・根拠は同じbatchで保存する。分析時に過去の訂正から出典を補う処理は行わない。
- 通常版・ダーク版の理解と嗜好を監査する。候補だけでなく入力、収集・保存済み資料、確認済み理解を参照し、人物への好意と道徳的支持、外部支配と本人の意思、肯定と否定を区別する。
- 根拠不足による候補0件を正常な結果として扱う。確認画面から追加質問への回答、または最大6件の仮説を使える。仮説は専用のプレビューへ保存し、選択して決定するまで分析・集計に含めない。決定後の再分析でも、既存の好みを保持する。
- 生成には属性・反応経路の定義・正負のスコア・条件・価値スタンスをセットで渡す。忠実／バランス／探索をrequired／include／exploreとして保持し、prohibitを必須の価値スタンスへ混ぜない。画面の詳細から反応・条件ごとに扱いを変えられる。
- 生成は同一briefから3案を作り、各案を独立検査し、必要なら1回修正する。必須・禁止・共通方針の判断不能、検査の欠落・重複・矛盾、実設定を指さないPointerは不合格となる。合格した案だけを比較し、最終採用はユーザーが選ぶ。全案不合格なら生成失敗となる。
- 独創性は同じ所有者・領域の登録人物、過去の生成、今回の合格済み案と照合する。名前の一致、設定本文の3文字の組み合わせによるJaccard係数、埋め込みのcosine類似度を使用する。既定閾値は名前0.92、設定の組み合わせ0.86、意味0.90。Fake環境のベクトルを意味的な類似度としては使用しない。
- 設定の個々の文字列へ「合う／合わない／混在」、理由、属性、反応、条件を記録できる。保存時はproposedで、明示的な確認後にだけプロフィールを再構築する。生成履歴の削除後も、ユーザーが確認した評価と対象設定の写しは保持する。同じ生成案への複数の評価は、履歴削除後も同一人物の根拠として集計する。

評価を保存する操作とプロフィールへ反映する操作は分かれている。古い解析の確認や遅れて届いた再実行は、新しい追加回答の解析を置き換えない。

独創性検査の登録人物側は、現在の確認済み・訂正済み属性から本文を組み立てる。生成側は、価値観やダーク版固有の設定も含めた本文全体を対象とする。長い本文はUTF-8で6000バイト以下に分割し、各部分の埋め込みを長さで加重平均する。本文後半の切り捨ては行わず、所有者・出典・本文ハッシュ・モデル・計算方式ごとにキャッシュする。

## 保存形式とAPI

品質管理の4テーブルと分析の品質情報は`001_initial.sql`に定義する。旧DBからの追加マイグレーションは提供しない。

| 対象 | 契約・保存先 |
| --- | --- |
| 新しい生成指示 | `GenerationBrief.schemaVersion = "2.0"`のみ |
| 新しい分析の来歴 | `analysis_runs.quality_context_json.schemaVersion = "2.1"` |
| 各生成案・検査・比較・採用 | `generation_candidates` |
| 類似度計算のキャッシュ | `character_similarity_documents` |
| 未確認／確認済みの評価 | `generation_feedback` |
| 元の登録を変更しない追加回答 | `preference_refinements` |

新しいAPIは通常版`/api/v1`、ダーク版`/api/v1/dark`の両方で利用できる。認証、CSRF、領域・所有者の分離、入力チェックを既存の共通処理へ接続している。

| メソッド・パス | 用途 |
| --- | --- |
| `POST /entries/:id/preference-input` | 質問回答は`mode: questions`、仮説作成／再作成は`mode: hypotheses`、選択決定は`mode: selection`。Idempotency-Key必須 |
| `POST /generation-requests/:id/selection` | 合格した`candidateId`を採用 |
| `GET /generation-feedback` | 評価と利用可能な属性を取得 |
| `POST /generation-feedback` | 設定・属性・反応・条件・理由を候補として記録。Idempotency-Key必須 |
| `POST /generation-feedback/:id/review` | `decision: confirm`または`reject` |

生成要求には`profileSnapshotId`が必須で、画面に表示された固定スナップショットを指定する。生成済み履歴は合格した`candidates`を持つ現行成果物だけを返す。失敗・処理中の履歴では候補は空配列となる。詳細な入力契約は[as-built OpenAPI](詳細設計/api/openapi.as-built.json)を参照。

エクスポートには新しい候補・評価・追加回答・類似度キャッシュも含める。バックエンドの追加AI処理に合わせ、生成Workflowの上限と実行leaseは90分、分析は30分とした。

## 実モデル評価

評価は一時的なSQLiteをD1互換アダプター経由で使用する。実際の理解・確認・嗜好分析・監査・生成処理を呼び、入力、出力、検査、モデル実行情報、ソースのハッシュを保存する。アプリの登録データは使用しない。確認操作は評価用の模擬操作であり、実ユーザーの採用率には数えない。

```sh
# 67件の固定入力をFakeで実行する配線・契約の確認
npm run eval:quality -- --provider fake --output /tmp/quality-fake.json

# 同じモデル・入力による比較。既存の出力ファイルへの上書きは禁止
npm run eval:quality -- --provider openai --limit 6 \
  --compare docs/evaluations/quality/baseline-openai-v1.json \
  --output /tmp/quality-new-run.json

# 特定ケースで3案生成と実際の埋め込みによる検査まで実行
npm run eval:quality -- --provider openai --only standard-narrative \
  --generate --embedding-provider openai --output /tmp/quality-generation.json
```

`--provider openai`はローカルの`.dev.vars`から接続設定を読み込む。キーをレポートへ出力しない。`--only`はカンマ区切りでケースを指定でき、`--model`でモデルを指定できる。比較対象のモデル・provider・fixture版・ケースの順序が異なる場合は比較を拒否する。

固定入力は[worker/evaluation/cases.ts](../worker/evaluation/cases.ts)。通常4例と既存ダーク63例を含む。訂正・削除、採用／禁止、検査の欠落・矛盾、追加回答と採用前の非集計は、実DBスキーマを使う[結合テスト](../tests/quality-pipeline.test.ts)と[検査テスト](../tests/generation-quality.test.ts)でも確認する。

補強後には条件付きの肯定・否定が両方残った。憧れの例では`wishful_identification`だけが残り、`admiration`の候補が出なくなったため、単純な反応経路の一致数は減った。この減少が適切かどうかも意味的レビューの対象となる。これは小規模・各1回の比較で、総合的な品質向上率は確定していない。出典の照合率も、意味の正しさ全体を保証する指標ではない。実ユーザーの訂正率と採用率は未測定で、レポートではnullとする。

通常版の実生成では3案すべてが条件・類似度検査に合格した。ダーク版の初回実生成ではPointerに不要な`/candidate`階層を含む等の問題により2案を除外し、合格した1案だけを提示した。この観測を受けてPointerのルートに関する指示を補強した。次の実行で修正時のbrief ID不一致が発生したため、生成・修正のスキーマに正しいIDを固定し、不一致も検査違反として処理するようにした。その後のダーク版の実生成では3案すべてが合格した。

生成評価後に追加した全文分割処理は、保存済みの生成設定を実Embedding Providerへ渡す別の検証で確認した。この検証は同一設定の検出とキャッシュ再利用を対象とし、生成品質の再測定には数えない。

既存の`eval:dark:gate`が要求する全次元の意味的正解率や不要な善化の採点を、反応経路の一致率で代用してはいない。保存した出力には人手での意味的レビューが必要であり、この比較だけで既存のダーク版リリースゲート通過とは扱わない。

## 追加質問・仮説選択の修正（2.1）

追加質問は、不明点の説明ではなく`recommendedQuestion`を表示する。古い結果で質問がない・疑問文になっていない場合も、対象について好き・苦手や場面を尋ねる質問文へ補う。

「仮説候補から選ぶ」は、既存の分析を維持したまま専用の枠へ候補を表示する。候補の作成・再作成では`analysis_runs`や`preference_assertions`を追加・更新しない。枠内のチェックボックスで選び、「決定」で初めて選択分を明示的な追加入力として再分析する。未選択の仮説は好みの根拠として渡さない。「仮説候補を再作成する」では以前の候補との重複を避け、選択をリセットする。候補が0件でも再作成と質問回答を使える。

再分析では、直前の分析の有効な好み・価値スタンスを、訂正状態・明示性・confidence・条件・根拠ごと新しい分析へコピーする。削除・差し替え済みの行は除外し、新規候補との完全な重複を抑える。履歴の元の行は書き換えない。質問への回答による再分析にも同じ保持処理を適用する。最終的な「好みの確認」までは新しい候補をプロフィールへ集計しない。

`mode: selection`には`hypothesisBatchId`と`selectedHypothesisIds`を指定する。所有者・領域・登録・元分析・最新プレビューを照合し、別ユーザーや古い候補、不正なID、空・重複選択を拒否する。再読み込み後も候補の内容は保存されている。

`001_initial.sql`で`preference_refinements`の`context_json`と`hypotheses_json`を定義する。`context_json`に元分析と選択内容、`hypotheses_json`に未選択の候補プレビューを保存する。選択決定の保存上のmodeは`questions`で、選択した好みの文章を回答として記録する。新しい分析の品質契約と仮説プロンプトは2.1。既存の結果は変更しない。

ローカルDBは`backups/preference-hypotheses-before-v2.1-20260905.sql`へ退避してから005を適用済み。本番のDBとデプロイは変更していない。


[実モデルでの追加検証](evaluations/quality/refinement-openai-v1.json)では、通常版で5件→再作成4件、ダーク版で6件→再作成3件の候補を得た。作成・再作成の間、既存の分析IDと候補は変わらなかった。両版とも1件を選び、既存の好みと選択分が再分析に残ることを確認した。初期理解・初期嗜好はFakeによる固定データで、仮説作成・再作成・選択後の分析／監査を実モデルで実行した。人による採用率や仮説の意味的な正解率を測ったものではない。

初回の選択後分析では、モデルが条件を分解して返した候補と補完用候補が重複した。選択内容の入力Pointer・属性・反応・好悪が一致するモデル候補を優先し、欠落した選択だけを補うよう修正した。[同じ仮説を使った再検証](evaluations/quality/refinement-openai-v2.json)では、通常版は既存1件＋選択1件＝2件、ダーク版は既存2件＋選択1件＝3件となり、選択分の重複がないことを確認した。モデルが分解した条件と、ユーザーが選んだ元の範囲は両方保持する。

修正後の`npm run verify`は成功し、テスト226件・E2E14件が通過した。仮説の導線は通常版・ダーク版ともChromiumで操作し、1366pxと320pxの表示、キーボード選択、選択のリセット、既存候補の保持を確認した。既存のlint警告87件とWebKitのホスト依存による除外は変わっていない。
