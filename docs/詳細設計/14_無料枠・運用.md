# DD-14 Cloudflare無料枠・運用詳細設計

## 1. 運用profile

初期profileは`free_validation`とし、個人開発、デモ、招待制の少人数検証だけを対象にする。

```typescript
interface FreeValidationAssumption {
  maxActiveUsers: 50;
  expectedDailyActiveUsers: 20;
  expectedConcurrentUsers: 5;
  availabilityTarget: "best_effort";
  rpoHours: 24;
  rtoHours: 4;
}
```

これはCloudflareが保証する利用者数ではない。実測したrequest、rows read/write、Workflow step、Queue operation、vector dimensionから継続可否を判断する。

外部LLM/Embedding Providerの料金・quotaは本書のCloudflare無料枠から分離する。ただしLLM jobの開始可否、同時実行、失敗率は同じcapacity画面で観測できるようにする。

## 2. 外部上限の基準

2026-08-29にCloudflare公式資料を確認した値である。実装開始時、preview公開前、本番公開前、以後月1回再確認し、変更はADRと構成更新で反映する。

| 製品 | Freeの主な外部上限 | 本設計上の注意 |
|---|---|---|
| Workers | 100,000 request/日、CPU 10ms/invocation、memory 128MB、subrequest 50/invocation | Workflow invocationとrequest枠を共有。重い集計を同期APIへ置かない |
| D1 | rows read 5,000,000/日、rows written 100,000/日、storage 5GB/account | Freeは1 database最大500MB。初期の単一D1ではこちらが先に効く |
| D1 Time Travel | Freeは7日 | 日次exportと併用する |
| R2 Standard | 10GB-month/月、Class A 1,000,000/月、Class B 10,000,000/月 | Free allocationはStandardだけ。Infrequent Accessを使わない |
| Workflows | requestはWorkersと共有、3,000 steps/日、state 1GB、Free CPU 10ms/invocation、完了state既定保持3日 | resultを1MiB未満にし、大きい状態をD1/R2へ置く |
| Queues | 10,000 operations/日、retention 24時間 | 通常message配送はwrite/read/deleteの3 operations。Outboxを正本にする |
| Vectorize | queried dimensions 30,000,000/月、stored dimensions 5,000,000 | 384次元なら保存約13,020 vectorが理論上限。余裕を持つ |

上限を超えたときの挙動やusage反映には遅延があり得る。アプリ内guardだけで「絶対に請求されない」ことを数学的に保証できない。Paid planや従量課金を自動有効化せず、別accountの他workloadと枠を共有しないことを運用条件とする。

## 3. Environment

| 環境 | Cloudflare resource | data |
|---|---|---|
| local-manual | local D1/R2 mock、in-memory vector、LLM/EmbeddingはWorkers AI既定（AI bindingのみremote） | synthetic only |
| local-test/CI | local D1/R2 mock、in-memory vector、LLM fake/replay | synthetic only |
| preview | preview用D1/R2/Vectorize/Workflow/Queue | synthetic＋同意済みtest user |
| production | production専用resource | real private data |

previewとproductionは同じaccountの無料枠を共有するため、preview workloadをproduction capacity計算に含める。load testはlocal/miniflareを主とし、Cloudflare上の大規模load testは禁止する。

binding:

```text
DB, OBJECTS, CHARACTER_ANALYSIS_WORKFLOW, GENERATION_WORKFLOW,
DELETION_WORKFLOW, DOMAIN_EVENTS, DEAD_LETTER_EVENTS,
SOURCE_VECTORS, CHARACTER_VECTORS, GENERATED_VECTORS
```

secret:

```text
AUTH_PEPPER, TURNSTILE_SECRET, OPENAI_API_KEY,
CAPACITY_ADMIN_TOKEN（管理scriptのみ）
```

`LLM_PROVIDER=workers_ai`または`EMBEDDING_PROVIDER=workers_ai`の場合はAPI keyではなく`AI` bindingを使う。AI modelはローカルにemulateされず、local-manualでは`remote: true`のdevelopment用bindingを使う。productionのOpenAI AdapterはWorker secretの`OPENAI_API_KEY`を使い、OpenAIの利用量と料金はCloudflare無料枠と合算しない。

ローカル手動確認ではページとD1/R2にsynthetic dataだけを使い、Workers AIへ実ユーザーdataを送らない。利用不可、quota不足、offline時は自動でFakeへ隠れて切り替えず、画面にProvider接続失敗を表示する。開発者が意図してoffline環境で再起動したときだけReplay／Fake動作へ切り替える。

secretを`.dev.vars`以外のtracked file、D1、log、client bundleへ入れない。

## 4. DeploymentProfile Strategy

```typescript
type CapacityLevel = "normal" | "warning" | "conservation" | "restricted" | "unavailable";

interface AdmissionDecision {
  allowed: boolean;
  level: CapacityLevel;
  code?: "USER_QUOTA_EXCEEDED" | "CAPACITY_DEGRADED" | "CAPACITY_UNAVAILABLE";
  retryAfter?: string;
  degradation?: string;
  reservations: CapacityReservation[];
}
```

判定順:

1. account/user状態とsecurity rate limit
2. user daily quota
3. 機能別concurrency
4. resource別app counter＋安全margin
5. Cloudflare usage snapshot
6. operationのworst-case予約量

Cloudflare usage値が6時間以上更新されていない場合は`conservation`へする。API成功後に実測D1 meta等で予約と実績の差を補正する。

## 5. Resource threshold

| resource | warning 70% | conservation 85% | restricted 90% | period |
|---|---:|---:|---:|---|
| Worker/Workflow request | 70,000 | 85,000 | 90,000 | UTC日 |
| D1 rows read | 3,500,000 | 4,250,000 | 4,500,000 | UTC日 |
| D1 rows written | 70,000 | 85,000 | 90,000 | UTC日 |
| single D1 storage | 350MB | 425MB | 450MB | current |
| Workflow steps | 2,100 | 2,550 | 2,700 | UTC日 |
| Workflow state | 700MB | 850MB | 900MB | current |
| Queue operations | 7,000 | 8,500 | 9,000 | UTC日 |
| R2 storage | 7GB-month | 8.5GB-month | 9GB-month | month |
| R2 Class A | 700,000 | 850,000 | 900,000 | month |
| R2 Class B | 7,000,000 | 8,500,000 | 9,000,000 | month |
| Vectorize queried dimensions | 21,000,000 | 25,500,000 | 27,000,000 | month |
| Vectorize stored dimensions | 3,500,000 | 4,250,000 | 4,500,000 | current |

`warning`は通知のみ、`conservation`は高コストbackgroundを遅延、`restricted`は新規高コスト操作を拒否する。外部上限の変更時は絶対値を更新し、割合ruleは維持する。

## 6. 予約容量

restricted閾値より外部上限までの10%を、次の優先操作用に残す。

1. login/session/logout/key rotation
2. account deletion
3. data export
4. private data read
5. review/correctionの保存
6. nonterminal jobの安全なcheckpoint/terminal化

新規user、upload、analysis、generation、全体rebuildは予約量を消費できない。削除がR2/Vectorize上限で止まる場合も、削除intentとD1 auth失効は先に完了し、派生削除を翌periodへ継続する。

## 7. 機能別quota・concurrency

user quotaは濫用防止上限であり、platform capacityを保証しない。

| capability | user上限 | platform同時実行 | 備考 |
|---|---:|---:|---|
| analysis | 30/UTC日 | 2 | 通常検証では1人3/日をsoft guide |
| generation | 10/UTC日 | 1 | 部分修正も1回 |
| profile rebuild | 20/UTC日 | userごと1 | eventをcoalesce |
| graph rebuild | 20/UTC日 | userごと1 | latest generationだけ |
| upload | 20MiB/entry、100MiB/user/月 | 2 upload | 1file 10MiB |
| export | 2/UTC日 | 1 | 24時間保持 |
| active user | 50 account合計 | - | operatorが引上げるまでregistration close |

capacity計算の暫定予約量:

| operation | Workflow steps | D1 write rows | Queue ops | 備考 |
|---|---:|---:|---:|---|
| existing analysis | 14 | 250 | 30 | assertion 100件想定 |
| custom analysis | 16 | 350 | 36 | delta 50件想定 |
| original analysis | 12 | 220 | 24 | source少量 |
| profile+graph rebuild | 8 | 500 | 12 | 既存projection入替 |
| generation | 9 | 120 | 12 | repairなし |
| account deletion | 10 | 2,000 | 60 | 最優先、実データで補正 |

予約量を確保できないcommandは429で受け付けない。すでに受けたJobのretryは予約済みbudget内で行う。

## 8. 縮退順

| level | 停止/縮退 | 維持 |
|---|---|---|
| warning | banner、operator通知 | 全機能 |
| conservation | vector全再構築、過去世代graph cache、batch再解析を延期 | interactive解析・生成 |
| restricted | 新規生成→新規解析→大容量upload→新規userの順に停止 | read、review、auth、export、削除 |
| unavailable | non-essential readもcache/summaryへ縮退 | auth失効、削除intent、capacity status |

Vectorizeだけrestrictedの場合、明示source選択/keyword検索へ縮退する。R2だけrestrictedの場合、inline text 100KiBまで許可する。Graph rebuild停止時もlist viewを維持する。

error response:

```json
{
  "error": {
    "code": "CAPACITY_DEGRADED",
    "message": "現在、解析の新規受付を一時停止しています。保存済みデータの閲覧と訂正は利用できます。",
    "requestId": "00000000-0000-4000-8000-000000000000",
    "details": {
      "capability": "analysis",
      "level": "restricted",
      "retryAfter": "2026-08-30T00:10:00.000Z"
    }
  }
}
```

内部resource名や正確な残量を一般ユーザーへ公開しない。

## 9. Source extraction

Workers FreeのCPU 10msでPDF解析・OCRを安定実行する前提にしない。

```text
SourceExtractionStrategy
├─ PlainTextWorkerExtractor       # text/plain, text/markdown
├─ BrowserAssistedPdfExtractor    # free_validation既定、PDF.js Web Worker
└─ ExternalDocumentExtractor      # 将来/OCR、別料金
```

- browser抽出結果はユーザー提供dataとしてhash/size/schema検証後に保存する
- PDF原本はR2に保持し、page locatorと抽出結果hashを関連づける
- scanned PDF/imageのOCRが必要なら`extraction_unavailable`としてmanual text入力を促す
- 外部抽出を有効にした場合はconsent、費用、保持設定を別途決める

## 11. Alert

| severity | 条件 | 対応目標 |
|---|---|---|
| info | 70%到達、single job retry | 翌営業確認 |
| warning | 85%到達、outbox age 30分、LLM failure 10%/15分 | 2時間以内 |

## 12. Backup・restore

### 12.1 Backup

- D1 Time Travel 7日を第一の短期復旧手段とする
- 日次でschema version、table件数、重要aggregate hashを記録する
- 週次でencrypted D1 exportを運用者管理storageへ作成し、30日保持する
- R2 source原本はD1 manifestのobject key/hashと照合する
- Vectorize、GraphProjection cacheはbackupせず再構築する
- backup accessをapplication secretと分け、restore操作をauditする

実ユーザーdataのbackupを開発端末へ常設しない。

### 12.2 Restore rehearsal

月1回previewで次を行う。

1. 空のpreview resourceを用意する。
2. D1 backup/Time Travel cloneから復元する。
3. migrationを最新まで適用する。
4. foreign key、件数、aggregate hashを検査する。
5. R2 manifestをsample照合する。
6. Vector/Graphを再構築する。
7. E2E smokeを通す。

目標RPO 24時間、RTO 4時間はbest effortでありSLAではない。

## 13. Deployment

```text
lint/typecheck/schema validation/unit
  → migration dry-run/local integration
  → preview deploy
  → preview contract/E2E/security smoke
  → production DB backup point確認
  → expand migration
  → Worker deploy（段階的trafficが可能なら使用）
  → health/capacity/auth/entry smoke
  → 30分監視
```

- migrationとcodeはbackward compatibleなexpand-first
- production secret/binding欠落時はstartup healthを失敗させる
- deployから課金plan変更を行わない
- rollbackは旧Worker versionへ戻し、schemaはforward compatibleに保つ
- destructive contract migrationは別releaseで行う

## 14. Runbook

### 14.1 D1 limit/overload

1. capacityをrestrictedへ固定する。
2. full scan route、slow query、rows readを確認する。
3. queued rebuildを停止する。
4. index/query fixまたは日次resetを待つ。
5. 書込整合性とoutbox欠落を検査する。
6. 連続発生ならPaid D1またはRDB移行ADRを開始する。

### 14.2 Queue retention超過

1. consumerを停止し原因を直す。
2. D1 outboxのpending/deadをsourceに再配送する。
3. event世代を確認し、古い派生更新はno-opにする。
4. Vector/R2/Graphの件数・hashを照合する。

### 14.3 LLM Provider障害

1. circuit breakerを開き新規LLM stepを`retrying`へし、次回時刻を設定する。
2. read、review、brief編集を維持する。
3. fallback Providerはdata policyとeval gate通過済みの場合だけ切り替える。
4. 回復後concurrency 1から徐々に再開する。

### 14.4 誤った解析の多発

1. prompt/model versionを停止する。
2. affected run metadataから範囲を特定する。
3. Profile currentを直前generationへ戻す、または影響assertionを保留する。
4. fixtureを追加し、修正版を評価する。
5. ユーザー訂正を上書きせず再解析候補を提示する。

## 15. 将来拡張trigger

次のいずれかが2週間中5日以上続いたら`scaled_production`検討を開始する。

- Worker/D1/Workflow/Queueの日次使用量70%以上
- single D1 storage 350MB以上または月10%以上増加
- capacity理由の解析・生成拒否が要求の5%以上
- Queue oldest age 15分超、Profile更新p95 10分超
- D1 query p95 300ms超またはoverload発生
- active user 50、DAU 20、同時5を継続超過
- SLA、全ユーザー横断graph、collaboration等が要件化

拡張順は、同一Cloudflare製品の有料化、query/retention最適化、Repository/Vector/Graph Strategy差替え、最後にservice分割とする。切替えは費用見積り、負荷試験、data migration、rollbackの承認後に手動実施する。
