# DD-06 D1データベース詳細設計

## 1. 位置付け

D1は初期構成における唯一の正本データベースである。登録原文、履歴、根拠、ユーザー確認、解析結果、生成条件、ジョブ状態を保持する。R2、Vectorize、ブラウザ用GraphProjectionはD1から再構築できる派生データとする。

初期DDLの正式版は[001_initial.sql](database/001_initial.sql)とする。本書はテーブルの責務、アクセス経路、更新規則を定義する。

## 2. 物理規約

| 項目 | 規約 |
|---|---|
| 主キー | UUIDv4/UUIDv7を格納する`TEXT PRIMARY KEY` |
| 日時 | UTCのRFC 3339文字列を格納する`TEXT` |
| 真偽 | `INTEGER NOT NULL CHECK (value IN (0, 1))` |
| 列挙 | `TEXT`と`CHECK`。将来拡張頻度の高い分類は辞書テーブル |
| score | `REAL CHECK (value BETWEEN 0.0 AND 1.0)` |
| JSON | canonical JSON文字列を`TEXT`へ格納し、application schemaで検証 |
| hash | SHA-256小文字hex 64文字を`TEXT`へ格納 |
| revision | aggregate rootの`revision INTEGER`を楽観lockに使用 |
| soft delete | ユーザー表示対象は`deleted_at`、法的・安全上不要な実体は後段で物理削除 |

D1に依存するdate関数やJSON関数をdomain ruleへ持ち込まない。API層で時刻を生成し、Repositoryがその値をそのまま保存する。

## 3. テーブル群

### 3.1 認証・利用量

| テーブル | 正本となる情報 |
|---|---|
| `users` | ユーザー、状態、公開名、revision |
| `credentials` | access key digestと世代。平文は保存しない |
| `sessions` | session digest、CSRF digest、有効期限、失効日時 |
| `consents` | 規約・privacy・AI利用への同意履歴 |
| `request_rate_limits` | D1 fallback rate-limit bucket |
| `usage_daily` | ユーザー別・機能別の日次使用量 |
| `idempotency_responses` | mutationの冪等response。secret応答は再構成modeと非秘密metadataだけ |
| `platform_usage_counters` | 無料枠capacity guard用の概算値 |

### 3.2 Character catalog・登録

| テーブル | 正本となる情報 |
|---|---|
| `works`, `work_versions` | 作品identityと名称等の版 |
| `character_identities` | 媒体や場面を越えたキャラクターidentity |
| `character_representations` | 特定媒体・人格・場面・二次創作・original表現 |
| `representation_relations` | base以外の表現間関係 |
| `user_character_entries` | ユーザーの「好き」登録aggregateとsubmit前のmutable draft payload |
| `entry_revisions` | 登録原文・対象表現・嗜好入力の不変revision |
| `entry_assets` | entry revisionとsource document revisionの用途別関連 |

### 3.3 資料

| テーブル | 正本となる情報 |
|---|---|
| `source_documents` | 論理資料 |
| `source_document_revisions` | inline textまたはR2 objectを指す不変版 |
| `source_fragments` | 引用可能な範囲、位置、hash |
| `source_sets`, `source_set_versions`, `source_set_items` | 解析時点に固定した資料集合 |

`source_set_items`はdocumentではなく`source_document_revision_id`を参照する。原資料が更新されても過去解析の再現性を失わない。

`source_document_revisions`はupload予定時に`pending`で作成できる。finalize時にHEAD検証後`finalized`へし、以後は本文・object key・hash・sizeを変更しない。`extraction_status`だけは派生処理の技術状態として更新できる。

### 3.4 解析・訂正

| テーブル | 正本となる情報 |
|---|---|
| `model_run_metadata` | Provider、transport、Adapter version、要求/解決後model、prompt/schema version、token概算、hash |
| `character_understanding_runs` | 基本像抽出の試行と状態 |
| `character_understanding_snapshots` | 確定可能な基本像snapshot。資料評価、要約、不確実性もversioned JSONで保存 |
| `character_assertions` | 設定、行動、解釈に関する構造化主張 |
| `customization_deltas` | base表現からcustom表現への差分 |
| `understanding_reviews` | snapshotへのユーザー判断 |
| `analysis_runs` | 嗜好解析の試行と状態。明示/推測要約と不確実性を保存 |
| `evidence_fragments` | assertionから参照する証拠と支持方向 |
| `preference_assertions` | polarity、response channel、strength、context |
| `value_stance_assertions` | 悪・非道徳等への価値上の支持・拒否・無関心 |
| `preference_value_stance_links` | 嗜好と価値スタンスの明示的関連 |
| `assertion_reviews` | 嗜好・価値スタンスへのユーザー判断 |
| `user_correction_events` | 何をどう訂正したかのappend-only audit |

`evidence_fragments`は複数種のownerを持つpolymorphic tableである。applicationは`owner_type`に対応するownerの存在をtransaction内で検証する。SQLiteの外部キーだけでは表現しない。

### 3.5 属性辞書

| テーブル | 正本となる情報 |
|---|---|
| `attribute_schema_versions` | ontology公開版と状態 |
| `attribute_definitions` | 固定core、管理語彙、自由語の正規化先 |
| `attribute_aliases` | 表記揺れ・同義語 |
| `attribute_relations` | broader、narrower、related、opposed等 |
| `raw_attribute_mentions` | LLMまたはユーザーが用いた未正規化語 |
| `attribute_mappings` | raw語から定義語への候補・採用結果 |

自由語を捨てず、`raw_attribute_mentions.raw_label`を必ず保存する。未知語は強制的に近い「穏当な」属性へ丸めず、unmappedのままProfileへ表示できる。

### 3.6 Profile・GraphProjection

| テーブル | 正本または再構築用情報 |
|---|---|
| `profile_projections` | ユーザーの現在の集計世代・状態 |
| `profile_dimensions` | 属性×polarity×response channel×contextの集計値 |
| `profile_patterns` | 共起、対比、条件付き嗜好等の候補 |
| `profile_snapshots`, `profile_snapshot_items` | 生成時に固定する不変profile |
| `graph_projection_snapshots` | ブラウザへ配布するprojection世代 |
| `graph_projection_nodes`, `graph_projection_edges` | node/edge payload |

`profile_*`と`graph_projection_*`は派生表だが、説明可能性と生成再現性のため世代・入力hashを保持する。壊れた場合はassertion群から再計算する。

`profile_snapshots.reason`の`profile_rebuild`は嗜好集計世代の確定時に自動作成する不変snapshotを表す。`generation`等の利用目的とは区別する。

### 3.7 生成・feedback

| テーブル | 正本となる情報 |
|---|---|
| `generation_requests` | 生成要求、固定profile snapshot、制約、状態 |
| `generation_request_preferences` | include/exclude/weight調整 |
| `generation_briefs` | LLMへ渡す前の検証済み生成条件 |
| `generated_characters` | 一つの生成系列 |
| `generated_character_revisions` | 初版・部分修正版の不変出力 |
| `generation_basis_links` | 出力要素とprofile根拠の関連 |
| `similarity_check_results` | 既存キャラへの過度な類似の検査 |
| `feedback_events`, `feedback_attribute_ratings` | ユーザーによる明示評価 |

生成した事実だけではprofileを更新しない。`feedback_events.use_for_profile = 1`かつユーザーが明示確認した属性評価だけを、新しい解析根拠候補にする。

### 3.8 非同期・監査

| テーブル | 正本となる情報 |
|---|---|
| `jobs`, `job_attempts` | ユーザー可視の非同期状態とattempt。削除jobだけone-time status token digestを保持 |
| `outbox_events` | D1 commitと派生更新の橋渡し |
| `audit_events` | security・削除・重要変更の追跡 |

## 4. 主要制約

- private resourceは必ず`owner_user_id`を持ち、Repositoryの全queryでowner条件を必須にする
- `entry_revisions(entry_id, revision_number)`、各snapshot世代、各source versionは一意とする
- `active_revision_number=0`は未submit。draft PATCHはrootのpayload/revisionを更新し、submit時にEntryRevision 1以降を追加する
- append-only tableはUPDATEせず、status変更が必要なrun/jobだけを例外とする
- `character_representations.base_representation_id`のcycle、深度8超過はapplicationで拒否する
- active ProfileProjectionはユーザーごとに1行とし、新世代は同じ行をrevision付きで切り替える
- confirmed snapshot/itemは更新せず、訂正時に新世代を作る
- assertionの`superseded_by_id`は同種のassertionだけを参照する
- sourceなしのmodel knowledgeは`explicitness=model_knowledge`かつconfidence上限0.45とする

## 5. Transaction境界

D1 Adapterは`D1Database.batch()`をUnit of Workとして使う。次は同一batchでcommitする。

1. aggregate rootのrevision付き更新
2. append-only revision/snapshot/assertionのinsert
3. user-visible jobの更新
4. 対応する`outbox_events`のinsert

外部LLM、R2、Vectorize、Workflow APIをtransaction内で呼ばない。外部処理の結果は新しい短いtransactionで保存する。

楽観lockは次の形とし、`changes !== 1`なら`REVISION_CONFLICT`を返す。

```sql
UPDATE user_character_entries
SET status = ?, revision = revision + 1, updated_at = ?
WHERE id = ? AND owner_user_id = ? AND revision = ?;
```

## 6. 代表queryとindex

| Query | 主index |
|---|---|
| 公開active user一覧 | `idx_users_public_active` |
| session認証 | `idx_sessions_token_digest` |
| userの登録一覧 | `idx_entries_owner_status_updated` |
| entryの最新revision | `uq_entry_revisions_number` |
| job polling | `idx_jobs_owner_created`、`idx_jobs_status_next_attempt` |
| current assertion集計 | `idx_preference_assertions_owner_status`、`idx_value_stance_owner_status` |
| profile dimension一覧 | `idx_profile_dimensions_projection_rank` |
| graph配布 | `idx_graph_nodes_snapshot`、`idx_graph_edges_snapshot` |
| outbox配送 | `idx_outbox_delivery` |

List APIでOFFSET paginationを使用しない。`(sort_value, id)`の複合cursorを使う。

## 7. 削除

1. accountを`deleting`へ変え全sessionを失効する。
2. `DeletionWorkflow`がR2/Vectorizeの派生を先に削除する。
3. D1は子から親の順に明示削除する。`ON DELETE CASCADE`は漏れ防止であり、運用の削除順序を置換しない。
   FKを持たない`idempotency_responses.owner_scope`と期限付きrate-limit bucketもuser scopeで検索し削除する。
4. 全削除後、tombstoneを含まない完了auditを短期保存する。ユーザー入力本文・digest・識別可能なpayloadは残さない。
5. browserへcache purge tokenを返し、IndexedDBとCache Storageを削除する。

DeletionWorkflowは他Jobを削除し、削除Jobだけ`owner_user_id=NULL`、`target_id`を削除operation IDへ置換、`subject_ref_hash`を不可逆な運用追跡値へ置換して最大7日残す。状態参照tokenはdigestだけを保存し、完了24時間後または7日経過で削除する。

個別entryのarchiveは物理削除ではない。Profile再計算で除外し、ユーザーが明示削除した場合だけ関連資料を参照数確認後に物理削除する。

## 8. Migration

- migrationは連番、forward-only、適用後に内容を書き換えない
- schema変更はexpand → backfill → read切替 → contractの順にする
- D1の大量backfillを単一requestで実行しない。cursor付き管理jobに分割する
- migrationには適用前後の`PRAGMA foreign_key_check`と重要index確認を含める
- 本番相当データの匿名fixtureでmigration rehearsalを行う
- rollbackは逆DDLではなく、直前backup復元またはforward fixを原則とする

## 9. DB交換時の注意

SQL列名はRepository Adapter内部の実装詳細である。domain/serviceはテーブルやD1 result型を参照しない。PostgreSQL等への移行時は、Repository契約とtransaction意味論を保ち、JSON列、部分index、lockingだけを移行先に最適化する。
