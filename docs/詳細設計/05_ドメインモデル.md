# DD-05 ドメインモデル詳細設計

## 1. モデル化原則

- `CharacterIdentity`と`CharacterRepresentation`を分ける
- キャラクター理解とユーザー嗜好を別aggregateにする
- 原文、Revision、Snapshot、Correctionを保持し再計算可能にする
- ユーザーの明示・確認・訂正をLLM推測より優先する
- 好き、苦手、response channel、value stanceを分ける
- 悪、非道徳、善への無関心を値として正常に扱い、医学的・道徳的評価を付加しない
- 派生・二次創作・場面限定を一級のRepresentationとして扱う

## 5. UserCharacterEntry aggregate

```typescript
type RegistrationType = "existing" | "customized_existing" | "original";
type EntryStatus =
  | "draft"
  | "submitted"
  | "understanding"
  | "understanding_review"
  | "analyzing"
  | "analysis_review"
  | "active"
  | "failed"
  | "archived";

interface UserCharacterEntry {
  id: UUID;
  ownerUserId: UUID;
  registrationType: RegistrationType;
  status: EntryStatus;
  draft: { schemaVersion: "1"; payload: unknown; updatedAt: IsoDateTime | null };
  activeRevisionNumber: number;
  activeGeneration: number;
  revision: number;
}

interface EntryRevision {
  id: UUID;
  entryId: UUID;
  revisionNumber: number;
  representationId: UUID;
  sourceSetVersionId: UUID | null;
  knownScope: string;
  userCharacterView: string | null;
  preferenceInput: PreferenceInput;
  contentHash: ContentHash;
  createdAt: IsoDateTime;
}
```

- EntryRevisionはappend-only
- Entry入力の`preferenceContext`は任意とし、特定の時期・場面・人格・状態に限って好きな場合だけ保持する。内部の`knownScope`は`preferenceContext`がなければ「キャラクター全体」として導出する
- `registrationType=original`では`characterBasicInfo`を必須とする。これは既成キャラクターのシステム収集済み公開情報に対応する基本像の一次入力であり、任意の`referenceMaterial`、`userCharacterView`と別フィールドで保持する
- Entry入力の`referenceMaterial`は任意とする。入力時だけprivateなSourceDocument/Revision/Fragmentを作り、未入力時は`sourceSetVersionId=null`を許容する。既成キャラクターの基本像はシステム収集情報とモデル知識から構成する
- オリジナルでは`characterBasicInfo`を必ずprivateなSourceDocument/Revision/Fragmentへ固定し、`referenceMaterial`があれば区分見出しを付けて同じSourceSetVersionへ含める。このためオリジナルの`sourceSetVersionId`はnullにならない
- draft payloadだけはsubmit前の作業状態としてmutableであり、aggregate revisionで楽観lockする
- `activeRevisionNumber=0`はまだsubmit済みEntryRevisionがないことを意味する
- submit時にvalidation済みRevisionとSourceSetVersionを固定する
- active後の変更は新Revisionと新analysis generationを作る
- archiveで関連assertionを削除せず、最新Profile集計対象から除外する

## 8. CustomizationDelta

```typescript
type DeltaOperation =
  | "inherit"
  | "add"
  | "modify"

  | "invert"

  | "emphasize"
```

## 9. PreferenceAnalysis aggregate

```typescript
interface PreferenceAssertion {
  id: UUID;
  analysisRunId: UUID;
  entryRevisionId: UUID;
  characterIdentityId: UUID;
  representationId: UUID;
  attributeDefinitionId: UUID | null;
  rawMentionId: UUID | null;
  polarity: "positive" | "negative" | "mixed";
  responseChannel: ResponseChannel;
  strength: UnitInterval;
  explicitness: "user_explicit" | "user_confirmed" | "inferred" | "model_knowledge";
  confidence: UnitInterval;
  context: ContextCondition;
  evidence: EvidenceRef[];
  status: "proposed" | "confirmed" | "corrected" | "rejected" | "superseded";
  supersededBy: UUID | null;
}
```

`ResponseChannel`:

44種類を`shared/response-channels.ts`のcatalogで一元管理する。大分類は、一般的な反応、見た目・声・表現、自分との重なり・同一化、親しさ・関係性、物語・感情体験、自分への作用、価値観・逸脱・複雑な好意、文化・ファンダム・創作とする。

特に、共感と同情、尊敬と願望的同一化、知覚された類似と自己投影、同一化とパラソーシャルな親しさ、人物支持と物語上の興味、恋愛的魅力と性的魅力を別channelとする。label、説明、UI分類、LLMへ渡す定義は同じcatalogを正本とし、近似語を別channelとして追加しない。

不変条件:

- positiveは嗜好方向であり道徳的善を意味しない
- 1つのCharacterAssertionからPreferenceAssertionを自動確定しない
- `user_explicit`の根拠はユーザーの好きな理由、`user_confirmed`はreviewを必須とする
- mixedを便宜的に0へ相殺せず、positive/negativeの根拠を保持する

- Jobはユーザー向け進捗の正本、Workflow instanceは実行手段とする

- at-least-onceと重複実行を前提にconsumerを冪等にする

## 15. 状態遷移サービス

全状態遷移は「現在状態、command、遷移先、必要条件、生成event」のtable-driven実装とする。不正遷移は409 `INVALID_STATE_TRANSITION`とする。

Entryの主要遷移:

| current | command | next | guard |
|---|---|---|---|
| draft | submit | submitted | draft valid、EntryRevision作成可能 |
| submitted | startUnderstanding | understanding | capacity allowed |
| understanding | proposeUnderstanding | understanding_review | snapshot candidate exists |
| understanding_review | confirmUnderstanding | analyzing | required reviews complete |
| analyzing | proposePreferences | analysis_review | analysis candidate valid |
| analysis_review | confirmPreferences | active | required reviews complete |
| active | createRevision | draft | new revision number |
| any nonterminal | fail | failed | error recorded |
| active/failed | archive | archived | owner command |

