# DD-02 画面・フロントエンド詳細設計

## 1. Route一覧

| 画面ID | Route | 認証 | 主要API |
|---|---|---:|---|
| SCR-00 | `/` | 不要 | `GET /users` |
| SCR-01A | `/register` | 不要 | `POST /users` |
| SCR-01B | `/register/activate` | 不要 | `POST /users/{id}/activate` |
| SCR-02 | `/login` | 不要 | `POST /sessions` |
| SCR-10 | `/entries` | 必要 | `GET /entries` |
| SCR-11 | `/entries/new` | 必要 | `POST /entries/drafts` |
| SCR-12 | `/entries/:entryId/edit` | 必要 | `GET/PATCH /entries/{id}` |
| SCR-13 | `/entries/:entryId/understanding` | 必要 | understanding API |
| SCR-14 | `/entries/:entryId/analysis` | 必要 | preference API |
| SCR-20 | `/profile` | 必要 | `GET /profile` |
| SCR-21 | `/profile/graph` | 必要 | graph API |

| SCR-31 | `/generated/:characterId` | 必要 | generated character API |

認証が必要なRouteで`GET /me`が401の場合は、元Routeを`returnTo`に保持して`/login`へ遷移する。`returnTo`は同一originの許可Routeだけを受理し、外部URLを許可しない。

## 2. Application shell

### 2.1 認証後navigation

```text
[嗜好プロフィール] [キャラクター登録] [キャラクター作成] [設定]
```

- desktopはheader navigation、狭幅はmenu buttonとdrawerにする
- 現在地は`aria-current="page"`で示す
- 最初のfocusable elementの前にメイン本文へのskip linkを置く
- ジョブ実行中は共通Job Centerに件数を表示する
- 無料枠警戒は黄、縮退はオレンジのbannerで表示し、色だけで状態を示さない

### 2.2 共通UI状態

| 状態 | 表示・動作 |
|---|---|
| initial loading | 項目構造が分かるskeleton。主要見出しは表示する |
| background refresh | 既存表示を残し、小さな更新表示 |
| empty | 空の理由と最初の操作を示す |
| validation error | field直下と先頭error summary。先頭不正fieldへfocus |
| recoverable API error | 入力を保持しretryを提供 |
| revision conflict | server版と自分の入力の差分を表示し、再読込みまたは新Revision作成 |
| capacity stop | 対象機能、理由、再開見込み、代替操作を表示 |
| unauthorized | CSRFとquery cacheを消去しloginへ遷移 |
| forbidden | 存在の有無を推測しにくい共通message |

### 2.3 Query key

```typescript
const queryKeys = {
  me: ["me"],
  users: (filter: UserFilter) => ["users", filter],
  entries: (filter: EntryFilter) => ["entries", filter],
  entry: (id: string) => ["entry", id],
  understanding: (id: string) => ["understanding", id],
  analysis: (id: string) => ["analysis", id],
  profile: ["profile"],
  graph: (snapshotId: string, detail: string) => ["graph", snapshotId, detail],
  generationRequest: (id: string) => ["generation-request", id],
  generatedCharacter: (id: string) => ["generated-character", id],
  job: (id: string) => ["job", id],
} as const;
```

mutation成功時は影響するqueryだけinvalidateする。logout、key rotation、account deletion開始時は全query cacheを消去する。

## 3. SCR-00 トップ・公開ユーザー一覧

### 3.1 項目

- サービス説明
- ユーザー名検索、0〜32文字
- activeユーザーのユーザー名とID
- ユーザー作成ボタン
- 選択ユーザーでloginするボタン

ユーザー名はlinkではなくselectable rowとし、IDを省略しない。検索は300ms debounce、Enterで即時実行する。結果は50件ずつ追加読込みする。

## 4. SCR-01 ユーザー作成・有効化

### 4.1 作成

| 項目 | 必須 | validation |
|---|---:|---|
| ユーザー名 | Yes | 正規化後1〜32 code points、制御文字不可 |
| Turnstile | Yes | productionでtoken必須 |
| データ取扱い同意 | Yes | 現行consent versionへ同意 |

submit後はaccess key保存stepへ遷移し、履歴backで作成formへ戻さない。

### 4.2 access key保存

- user ID、UUID access key、有効化期限の残り時間を表示する
- access keyの表示、copy、UTF-8 text file downloadを提供する
- clipboard失敗時も手動選択できる
- `保存しました`のcheckboxが有効になるまで有効化ボタンをdisabledにする
- keyはReact stateだけに持ち、URL、log、Web Storageへ出さない
- reloadした場合はkeyを再表示できないことを事前に警告する

### 4.3 有効化

- access keyをbodyで再送し、pending userをactiveにする
- 期限切れは`REGISTRATION_EXPIRED`とし、再作成導線を示す
- 成功後はlogin画面へuser IDだけを渡す。access keyは渡さない

## 5. SCR-02 ログイン

| 項目 | 必須 | validation |
|---|---:|---|
| ユーザー | Yes | SCR-00選択またはUUID直接入力 |
| access key | Yes | canonical UUID |
| Turnstile | Yes | productionでtoken必須 |

- access keyの初期typeは`password`、表示切替ボタンを持つ
- pasteを禁止しない
- 失敗時はユーザー不在とkey不一致を同じmessageにする
- 成功後はCSRF tokenをmemoryに保持し、`returnTo`または`/profile`へ遷移する
- key紛失の復旧機能は提供しない旨を表示する

## 6. SCR-10〜14 キャラクター登録

### 6.1 一覧

フィルター:

- status: draft / processing / review_required / active / failed / archived
- registrationType: existing / customized_existing / original
- work、文字列検索
- updatedAt range

各rowにキャラクター名、作品、登録方式、現在step、最終更新、要確認件数を表示する。draftの削除は確認dialog、activeの削除は影響するProfile再計算を明示する。

### 6.2 Wizard共通

```text
1. 登録方式
2. 対象・資料
3. キャラクター像確認
4. 好きな理由
5. 嗜好解析確認
```

- step 1完了時にserver draftを作成する
- step 2以降は1秒debounceでautosaveし、明示的な`一時保存`も提供する
- autosaveは同一内容hashを再送しない
- navigation前に未送信がある場合のみ破棄警告を出す
- step前進はserver validation完了後に許可する
- 古いanalysisがある内容を変更する場合は新EntryRevisionとし、既存Snapshotを更新しない

### 6.3 Step 1: 登録方式

| 値 | 表示 | 説明 |
|---|---|---|
| `existing` | 既成キャラクター | 作品内の基本的な人物像 |
| `customized_existing` | 既成キャラクター（カスタム） | 人格、場面、時期、二次創作、ユーザー解釈 |
| `original` | オリジナルキャラクター | ユーザーが定義する人物 |

### 6.4 Step 2: 既成キャラクター

| 項目 | 必須 | 上限・規則 |
|---|---:|---|
| 作品名 | Yes | 1〜200 code points |
| キャラクター名 | Yes | 1〜200 |
| 媒体・版 | No | 100 |
| 特に好きな時期・場面・状態 | No | 2,000 |
| 解析に加えたい参考情報 | No | 20,000 |
| 親しみ | No | `new` / `familiar` / `long_term` |
| あなた自身のキャラクター解釈 | No | 4,000 |
| ネタバレ範囲 | No | 1,000 |
| 資料 | No | 1file 10MiB、1entry合計20MiBかつ20filesを初期値 |

作品・キャラクター検索は重複候補を示すが、ユーザーが別表現と判断した場合は新規作成を許可する。

### 6.5 Step 2: 既成カスタム

既成の項目に加えて次を必要とする。

| 項目 | 必須 | 規則 |
|---|---:|---|
| 派生元Representation | Yes | 候補選択または先に既成登録 |
| カスタム種別 | Yes | `user_interpretation`（独自解釈）/ `transformative`（二次創作）/ `alternate_setting`（別設定）の順に表示 |
| 特に好きな時期・場面・状態 | No | 2,000。未入力時はキャラクター全体 |
| 基本像からどう違うか | Yes | 1〜8,000 |
| 継承要素 | No | 各500、50件 |
| 追加・変更要素 | Yes | 各2,000、50件 |
| 対象外要素 | No | 各500、50件 |
| canonicality | Yes | official / semi_official / transformative / user_interpretation |

### 6.6 Step 2: オリジナル

| 項目 | 必須 | 上限・用途 |
|---|---:|---|
| キャラクター名 | Yes | 200 |
| キャラクター基本情報 | Yes | 20,000。性格、価値観、目的、行動、関係性、物語上の役割など、基本像を構成する設定 |
| 特に好きな時期・場面・状態 | No | 2,000。未入力時はキャラクター全体 |
| 解析に加えたい参考情報 | No | 20,000。基本情報とは別に参照させる設定メモ・補足資料 |
| あなた自身のキャラクター解釈 | No | 4,000。基本情報・参考情報とは出所を分離する |

`characterBasicInfo`は、既成キャラクターにおける作品名・キャラクター名・媒体からのシステム収集済み公開情報に対応する。オリジナルではシステムによるキャラクター検索を行わず、このユーザー入力を基本像抽出の一次入力とする。

### 6.7 Step 3: キャラクター像確認

- assertionをカテゴリ別に表示する
- 各assertionに値、scope、設定/行動/解釈、根拠、明示性、信頼度を表示する
- 根拠は必要なときだけ展開し、原文と出典を区別する
- decisionはconfirm / correct / reject / conditional
- correctは元assertionを上書きせずCorrectionを作成する
- カスタムは左にbase、右にcustom、中央にDelta operationを表示する
- 必須確認項目が0件、未解決矛盾が0件になるまでstep 4へ進めない

### 6.8 Step 4: 好きな理由

| 項目 | 必須 | 規則 |
|---|---:|---|
| 好きな点 | Yes | 1〜10,000 |
| 苦手な点 | No | 10,000 |
| 特定場面・台詞 | No | 各2,000、20件 |
| response channel | No | 複数選択、未指定可 |
| 価値スタンス | No | 対象ごと、`unspecified`可 |
| 条件・例外 | No | 4,000 |

悪・非道徳・善への無関心そのものが好きと明示できる専用の選択肢を、言い訳や否認を要求しない表現で提供する。

### 6.9 Step 5: 嗜好解析確認

- PreferenceAssertionとValueStanceAssertionを別sectionで表示する
- `positive`を`道徳的に良い`と表示しない
- 各候補にconfirm / correct / reject / conditionalを提供する
- `好きではなく面白い`はresponse channelを`narrative_interest`へ訂正する操作とする

response channelは、よく使われる9項目を常時表示し、詳細項目を「見た目・声・表現」「自分との重なり・同一化」「親しさ・関係性」「物語・感情体験」「自分への作用」「価値観・逸脱・複雑な好意」「文化・ファンダム・創作」のaccordionへ分ける。各項目には近似概念との違いが分かる短い説明を表示し、複数選択を許可する。catalogの全44項目と表示順は`shared/response-channels.ts`を正本とする。
- `属性は好きだがこの表現は苦手`はpositive assertionとcontext付きnegative assertionに分ける
- 価値スタンス未指定を道徳的拒否で補完しない
- 全必須確認後にProfile反映を実行する

## 7. SCR-20 嗜好解析結果

### 7.1 共通filter

- ProfileSnapshot: 最新または過去Snapshot
- 期間
- registration type
- work / CharacterIdentity
- polarity
- response channel
- explicitness
- confidence帯
- 条件付きのみ

filterはURL queryへ保持するが、自由記述やセンシティブ値をURLに入れない。

### 7.2 タブ

| タブ | 表示 |
|---|---|
| 概要 | stable/emerging傾向、response channel、データ品質、最終更新 |
| 属性詳細 | positive/negativeを別カラム、condition、根拠数、独立性 |
| 嗜好グラフ | GraphProjection、filter、表・リスト代替 |
| キャラクター別 | Identity→Representation→Assertion |
| 履歴・根拠 | Correction、ProfileSnapshot、根拠の遅延展開 |
| データ品質 | 独立キャラクター数、作品偏り、未確認、矛盾、推測率 |

- `データがない`はgrayの`未観測`、negativeは`苦手傾向`と明示する
- positive/negativeを差分だけで表示しない
- confidenceは数値と根拠構成をtooltipで説明する
- すべてのchartにtable表示を用意する

## 8. SCR-30〜31 オリジナルキャラクター作成

### 8.1 Step 1: 作成方針

- ProfileSnapshot選択。既定は最新だが、作成開始後はIDを固定する
- mode: faithful / balanced / exploratory
- 用途、世界観、ジャンル、想定役割

### 8.2 Step 2: 嗜好選択

各Profile itemに次を指定する。

```text
required / include / weak_include / explore / omit / prohibit
```

- positiveとnegativeを別々選択する
- value stanceをpreference attributeと混ぜない
- 閾値未満のitemを採用する場合は`推測の弱い傾向`と表示する

### 8.3 Step 3: GenerationBrief

- structured briefと人間向けsummaryを同時表示する
- 悪志向、非道徳、善悪無関心、自己規範、混合を選択できる
- 悲劇的過去、正当化、隠れた善性、改心、救済、贖罪、処罰、敗北、道徳的教訓の各項目を`required / allowed / prohibited / unspecified`で指定する
- briefを修正するとrevisionを増やし、以前の生成実行と混ぜない

### 8.4 Step 4: 生成・調整・評価

- job status、step、開始時刻、retryの有無を表示する
- 生成中に同じrequestの生成ボタンを再度有効化しない
- 結果はsection単位に表示し、全体再生成とsection部分修正を分ける
- 嗜好との対応は根拠IDとともに示すが、推測を確定的に表示しない
- 類似警告がある場合は対象と理由を示し、そのまま保存または再生成を選択する
- feedbackは総合とsection別。Profileへの候補反映は明示checkboxを既定OFFにする

## 9. SCR-40〜43 設定

### 9.1 基本情報

- user ID、username、作成日、データ件数概要
- センシティブなresponse channelの表示設定
- browser Graph cacheの容量と消去ボタン

### 9.2 access key変更

- 現在keyを再入力する
- 実行前に`全端末からlogoutされる`ことを確認する
- 新keyを一度表示し、保存確認後にloginへ遷移する

### 9.3 export

- JSON packageの対象カテゴリを表示する
- 実行はjobとし、完了後に短時間download URLを返す
- download後のobjectは24時間で削除する

### 9.4 account deletion

- 削除対象、復元できないこと、派生ストア削除に時間がかかることを表示する
- usernameを確認入力させる。access keyの再入力は必須にしない
- 開始後は直ちにsessionを失効し、完了画面はpublicのjob tokenを作らず、削除受付済みの固定messageとする

## 10. Job polling

- 開始後30秒は2秒間隔、5分まで5秒、以降15秒とする
- pageがbackgroundのときは30秒以上に抑制する
- `waiting_for_user`はpollingを停止し、対応画面への導線を示す
- `failed`はretryableの場合だけretryボタンを示す
- `429`と`Retry-After`は指定時間まで自動pollを止める
- 同じjobの複数componentからのpollはTanStack Queryで1requestに共有する

## 11. Accessibility

- WCAG 2.2 AAを受入基準とする
- Wizardはordered listと現在stepをscreen readerへ通知する
- modalはfocus trap、Escape、閉じた後のtrigger focus復帰を実装する
- toastだけで重要errorを通知しない
- 非同期statusは視覚的更新と`aria-live="polite"`を使い、過剰に読み上げない
- Graphは同じfilterのtable/list代替を必須とする
- positive/negative、confidence、statusは色とtext/iconの2種類以上で示す
- motionは`prefers-reduced-motion`に従う

## 12. Responsive・browser

- 360 CSS pxから機能を失わない
- 比較UIは狭幅で左右表示から縦積みへ変更する
- Graphは高さをviewportに合わせ、操作panelを画面外に押し出さない
- 実装開始時点の主要browser安定版と直1versionを対象とする
- WebGL利用不可時はGraph tableを既定表示にする
