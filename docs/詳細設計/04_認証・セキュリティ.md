# DD-04 認証・セキュリティ詳細設計

## 1. 認証不変条件

- email、password、OAuthを使わない
- user IDとUUID access keyで認証する
- access keyは作成または回転時に一度だけ平文表示する
- serverはaccess key、session token、CSRF tokenの平文を永続化しない
- key紛失後の復旧・再発行を提供しない
- key rotationは旧credentialと全sessionを失効させる
- sessionはHttpOnly cookie、CSRFはmemory tokenで保護する
- active userとactive credentialだけをlogin対象にする

## 2. 暗号プリミティブ

| 用途 | 方式 |
|---|---|
| HMAC | HMAC-SHA-256, key=`AUTH_PEPPER`, UTF-8 input, lowercase hex output |
| digest | SHA-256, UTF-8 input, lowercase hex output |
| random token | Web Crypto CSPRNG 32 bytes, Base64URL without padding |
| UUID derivation | HMAC先頭16 bytesをUUID形式にしversion nibble=4、variant=RFC 4122 |
| comparison | 長さの差を含めた定時間比較 |

`AUTH_PEPPER`は環境別に32 bytes以上のランダムsecretとする。通常運用中のpepper rotationは全credentialを使用不能にするため行わない。必要時は別の移行計画と全ユーザー再登録を要する。

## 3. ユーザー名

```typescript
function normalizeDisplayUsername(value: string): string {
  return value.normalize("NFKC").trim().replace(/\s+/gu, " ");
}

function normalizeUsernameForUniqueness(value: string): string {
  return normalizeDisplayUsername(value).toLocaleLowerCase("ja-JP");
}
```

- display usernameは正規化後1〜32 Unicode code points
- C0/C1制御文字、NUL、改行、TABを拒否する
- `username_normalized`にunique indexを持つ
- `pending`と`active`を同一性判定に含める
- `deleting`は新規同名登録を削除完了まで拒否する

## 4. ユーザー作成

### 4.1 入力

- `username`
- `consentVersion`
- `turnstileToken`
- header `Idempotency-Key`

### 4.2 決定論的出力

```text
userId    = deriveUuid(AUTH_PEPPER, "registration:user:" + idempotencyKey)
accessKey = deriveUuid(AUTH_PEPPER, "registration:key:"  + idempotencyKey)
```

credential digest:

```text
canonicalAccessKey = trim(accessKey).toLocaleLowerCase("en-US")
digestInput        = userId + NUL + canonicalAccessKey
credentialDigest   = HMAC-SHA-256(AUTH_PEPPER, digestInput)
```

### 4.3 処理

1. Origin、body、Idempotency-Keyを検証する
2. `REGISTRATION_MODE=open`かとcapacityを確認する
3. Turnstile Siteverifyを検証する
4. usernameを正規化し一意性を確認する
5. user IDとaccess keyを導出する
6. `pending` user、credential digest、consent、secretを除いたidempotency metadataを原子的に保存する
7. `expiresAt = now + 15 minutes`とする
8. user ID、access key、expiresAtを201で返す

同一Idempotency-Keyの再送はaccess keyを再導出して返す。idempotency response本文に平文keyを保存しない。異なるusernameでの再利用は409とする。

## 5. 有効化

1. `userId`と`accessKey`のUUID形式を検証する
2. pendingかつ`pending_expires_at > now`のuserとactive credentialを取得する
3. submitted credential digestを計算し定時間比較する
4. userを`active`、`activated_at=now`に変更する
5. `UserActivated`をOutboxに追加する

期限切れは410 `REGISTRATION_EXPIRED`、credential不一致は401 `INVALID_CREDENTIALS`とする。pending cleanupは1日1回以上行い、期限から24時間経過後に削除する。

## 6. ログイン・session作成

### 6.1 入力とtoken

```text
sessionToken = HMAC-SHA-256(
  AUTH_PEPPER,
  "session" + NUL + userId + NUL + idempotencyKey
)
sessionDigest = SHA-256(sessionToken)
csrfToken     = HMAC-SHA-256(AUTH_PEPPER, "csrf" + NUL + sessionToken)
csrfDigest    = SHA-256(csrfToken)
```

session tokenは64文字のlowercase hexとする。

### 6.2 処理

1. Origin、Turnstile、rate limit、Idempotency-Keyを検証する
2. user IDとaccess keyをcanonicalizeする
3. active userとactive credentialのみを取得する
4. credential digestを定時間比較する
5. sessionを`expiresAt = now + 30 days`で作成する
6. cookieとresponse bodyのCSRF tokenを返す

認証失敗はuser不在、status不正、credential不一致のどれも401 `INVALID_CREDENTIALS`とする。ログには内部reasonの分類だけをsecretなしで記録する。

## 7. Cookie・rolling renewal

```text
Set-Cookie: __Host-session={token}; Max-Age=2592000; Path=/; HttpOnly; Secure; SameSite=Strict
```

- Domain属性を付けない
- session残存期間が7日以下のrequestでexpiresAtをnow+30日へ更新する
- 同一sessionの更新は1日1回以下に抑えるため`last_renewed_at`を使う
- session解決時はtoken digest、`revoked_at IS NULL`、expiresAt、user statusを確認する
- CSRF tokenを再導出し、DBのcsrf digestと不一致ならsessionをrevokeする

## 8. Origin・CSRF

- GET、HEAD、OPTIONS以外は`Origin`必須とし、正確な`APP_ORIGIN`と比較する
- missing Originは403 `ORIGIN_REQUIRED`、不一致は403 `ORIGIN_DENIED`とする
- 認証済みmutationは`X-CSRF-Token`を必須とする
- header tokenとsessionから再導出したtokenを定時間比較する
- login後のCSRF tokenはmemoryに保持し、reload後は`GET /me`から再取得する
- CORSによる他origin公開を初期は行わない

## 9. レート制限・quota

| scope | 既定 | window | subject |
|---|---:|---:|---|
| public mutation | 30 | 10分 | IP HMAC |
| authenticated IP mutation | 120 | 1分 | IP HMAC |
| authenticated user mutation | 60 | 1分 | user ID HMAC |
| analysis | 30 | UTC 1日 | user ID |
| generation | 10 | UTC 1日 | user ID |
| recommendation | 20 | UTC 1日 | user ID |

- 初期値は環境変数で下げられるが、上げる場合はDD-14のcapacity評価を必要とする
- IP原文をDBに保存せず、`HMAC(AUTH_PEPPER, "rate-limit" + NUL + scope + NUL + subject)`を使う
- limit超過時は429と`Retry-After`を返す
- Turnstileはuser作成とloginに必須とする

## 10. Logout

1. current sessionの`revoked_at=now`とする
2. `__Host-session`を`Max-Age=0`で削除する
3. CSRF memory、TanStack Query cache、Graph IndexedDB namespaceをbrowserで削除する
4. 応答は204とする

sessionが存在しない場合もcookieを削除し204とする。

## 11. Access key rotation

```text
nextAccessKey = deriveUuid(
  AUTH_PEPPER,
  "rotation:key:" + userId + ":" + idempotencyKey
)
```

1. current access keyをcredential digestで再認証する
2. userのactive credentialを全てrevokeする
3. `version = max(version) + 1`のnew credentialを作成する
4. userの全sessionをrevokeする
5. new access keyを一度返す
6. current cookieを削除する

同一Idempotency-Keyの再送は、旧credentialがrevoked済みでも既存new credentialを確認し、同じnew access keyを返す。

## 12. Account deletion

- mutation受付時にuserを`deleting`とし、全credential・sessionをrevokeする
- 削除状態確認tokenは`HMAC-SHA-256(AUTH_PEPPER, "deletion-status-token" + NUL + jobId + NUL + idempotencyKey)`の256-bit Base64URLとする
- D1には`HMAC-SHA-256(AUTH_PEPPER, "deletion-status-digest" + NUL + jobId + NUL + token)`だけを保存し、冪等再送時はtokenを再導出する
- tokenは一度だけ応答し、比較は定時間、該当削除jobのGET以外へ利用しない
- D1の正本削除だけで完了とせず、R2、Vectorize、Graph cacheへの削除予定をjobで追跡する
- ブラウザは受付成功時にcookieと全local cacheを削除する
- shared catalog entityはuserの個人データが残らない場合のみ残せる。user-owned originalとcustom representationは削除する
- auditにはuser ID原文ではなく削除job IDとHMAC追跡値を残す

## 13. Security headers

| Header | 値の方針 |
|---|---|
| `Content-Security-Policy` | `default-src 'self'`; script/connect/frameにTurnstileと承認済LLM gatewayの必要最小限 |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `no-referrer` |
| `Permissions-Policy` | camera/microphone/geolocation等を既定拒否 |
| `frame-ancestors` | CSPで`'none'` |
| `Cross-Origin-Opener-Policy` | Turnstile動作を検証した上で`same-origin` |

inline scriptはnonceなしで実行しない。CSPの例外は自動testと手動browser testでTurnstileを含めて検証する。

## 14. データ分類と外部LLM

| データ | 分類 | 外部送信 |
|---|---|---|
| public user ID/name | 公開 | LLMへ送信不要 |
| 登録、好きな理由、嗜好 | 個人限定/センシティブ | 必要な断片だけ、consent範囲内 |
| 恋愛・性的response channel | センシティブ | 個別opt-inまたは除外 |
| access/session/CSRF/API key | 秘密 | 禁止 |

- Providerの学習利用と長期保存を無効にできないProviderはproductionで使わない
- prompt/response payload loggingはApplication、AI Gateway、Providerのすべてで既定OFFとする
- prompt injection対策としてsourceは命令ではなくquoted untrusted dataとして渡す
- LLMからのURL、tool call、HTML、scriptを実行しない

## 15. 脅威と対策

| 脅威 | 対策 |
|---|---|
| credential DB漏えい | HMAC digest、pepper分離、平文非保存 |
| session theft | Secure/HttpOnly/SameSite cookie、revoke、expiry |
| CSRF | strict Origin + session-derived CSRF header |
| XSS | React escaping、CSP、HTML sanitize、LLM HTML非実行 |
| IDOR | 全個人queryのowner condition、Repository契約test |
| login enumeration | 共通401、rate limit、Turnstile |
| botによる無料枠消費 | Turnstile、user quota、capacity policy、registration close |
| prompt injection | sourceをuntrusted data扱い、tool無効、schema検証 |
| 越権R2 access | private bucket、object owner再検証、短期単一操作URL |
| Vectorize間違い検索 | namespace/filterに加えD1でowner/revision再検証 |
| browser graph改ざん | server正本へ反映しない |
| ユーザー嗜好からの危険性推測 | LLM schemaとpromptで禁止、固定評価 |

## 16. Security test必須項目

- access key、session、CSRFの平文がD1・R2・logにない
- ユーザーAの全resource IDをユーザーBが参照・更新できない
- Origin missing・不一致、CSRF missing・不一致を拒否する
- key rotation直後に旧keyと旧sessionが使えない
- 同一Idempotency-Keyの同一・異なbodyを区別する
- account deletion受付直後からデータへアクセスできない
- LLM出力のHTML、URL、instructionが実行されない
