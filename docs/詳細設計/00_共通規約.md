# DD-00 共通規約

## 1. 規範語

- MUST / 必須: 実装・テストで必ず満たす
- MUST NOT / 禁止: 実装してはならない
- SHOULD / 推奨: 異なる実装にはADRと同等の根拠が必要
- MAY / 任意: 契約を崩さない範囲で選択可能

## 2. 言語・命名

| 対象 | 規則 | 例 |
|---|---|---|
| TypeScriptの型・class | PascalCase | `CharacterRepresentation` |
| TypeScriptの値・関数 | camelCase | `profileSnapshotId` |
| DBのtable・column | snake_case | `profile_snapshot_id` |
| HTTP JSON | camelCase | `sourceSetVersionId` |
| enum値 | lowercase snake_case | `waiting_for_user` |
| domain event | PascalCase過去形 | `ProfileProjectionUpdated` |
| Queue event type | dot区切り | `profile.projection.updated.v1` |
| R2 key | lowercase fixed prefix + UUID | `v1/users/{userId}/sources/{sourceId}/revisions/{revisionId}/original` |
| metric | lowercase snake_case | `workflow_step_failed_total` |

ユーザー表示は日本語を初期言語とする。ドメイン名、API、DB、eventは英語で安定させる。

## 3. ID・時刻・数値

### 3.1 ID

- 全エンティティIDは小文字canonical UUID文字列とする
- 通常のIDはWeb Cryptoの`crypto.randomUUID()`でアプリケーション側が生成する
- ユーザー作成時のaccess keyとsession tokenはDD-04の方式に従う
- 外部ProviderのIDを主キーにしない
- APIはUUIDを小文字へcanonicalizeし、不正形式を`VALIDATION_ERROR`とする

### 3.2 時刻

- ApplicationとAPIはUTCのRFC 3339文字列を使う
- D1は`TEXT NOT NULL`のUTC ISO 8601、常にミリ秒と`Z`付きで保存する
- 日次quotaの日付はUTCの`YYYY-MM-DD`とする
- 表示時だけbrowser local timeへ変換する
- 時刻の比較はDB文字列の同一canonical formatまたはApplicationのepoch変換後に行う

### 3.3 数値

- 比率、強度、信頼度、重みは`0.0 <= value <= 1.0`のREALとする
- 回数、version、並び順は0以上のINTEGERとする
- APIは`NaN`、`Infinity`、`-Infinity`を受理しない
- 集計中間値は倍精度、永続化時は小数点以下6桁へ丸める

## 4. 文字列・Unicode

- ユーザー名はNFKC正規化、前後空白除去、連続空白を1文字へ圧縮する
- ユーザー名の一意性用は上記後に`toLocaleLowerCase("ja-JP")`する
- 自由記述、台詞、引用原文は自動NFKC変換せず、入力原文を保存する
- 検索用normalized値は原文と別columnまたは別インデックスとする
- C0/C1制御文字とNULは表示名・検索語・説明項目で拒否する。改行可能な自由記述はTAB、LFだけ許可する
- 文字数はUnicode code point単位で数える。byte数の上限は別途UTF-8で検査する

## 5. JSON・Schema

- API request/responseはOpenAPI 3.1とJSON Schema 2020-12を正式契約とする
- requestは原則`additionalProperties: false`とする
- 永続化するJSONは`schemaVersion`を必須とする
- JSONの未指定はproperty省略、明示的な空値は`null`とし、同義にしない
- arrayの順序が意味を持たない場合はIDでsortしてhashを計算する
- content hashはUTF-8のcanonical JSONへSHA-256を適用する
- LLM生出JSONは受信後にZodで再検証し、不正データをドメインentityへ変換しない

## 6. API envelope

### 6.1 成功

```json
{
  "data": {},
  "meta": {
    "requestId": "00000000-0000-4000-8000-000000000000"
  }
}
```

一覧は`meta.page`を持つ。

```json
{
  "data": [],
  "meta": {
    "requestId": "00000000-0000-4000-8000-000000000000",
    "page": {
      "nextCursor": null,
      "hasMore": false
    }
  }
}
```

### 6.2 エラー

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容を確認してください",
    "requestId": "00000000-0000-4000-8000-000000000000",
    "details": {
      "fields": [{ "path": "username", "reason": "too_long" }]
    }
  }
}
```

- ユーザー向けmessageにsecret、SQL、stack trace、Provider生応答を含めない
- `requestId`は応答headerの`X-Request-Id`と一致させる
- retry可能時はHTTP `Retry-After`と`details.retryAfter`を返す

## 7. HTTP・キャッシュ

- API base pathは`/api/v1`とする
- JSONは`Content-Type: application/json; charset=utf-8`とする
- 個人データ応答は`Cache-Control: no-store`とする
- JSON bodyのApplication上限は1MiBとする。ファイルはR2直接uploadを使う
- `ETag`はrevisionまたはprojection hashとし、更新時は`If-Match`を使う
- 日時、enum、IDはlocaleに依存しない

## 8. 冪等性

- GET、HEAD、OPTIONS以外は`Idempotency-Key`を必須とする
- keyはcanonical UUIDとする
- scopeは`user-or-public-subject + method + normalized-path + key`とする
- request bodyのSHA-256を保存し、同じscopeで異なるbodyが来たら`409 IDEMPOTENCY_KEY_REUSED`とする
- 成功応答と再現可能な4xx応答を24時間保持する
- access key、session/CSRF、削除status tokenを含む応答は平文responseを保存せず、`response_mode`と非秘密metadataを保存してDD-04の決定論的導出で再構成する
- ユーザー作成時の平文access keyは一度だけ返し、永続化しない
- WorkflowとQueue consumerは`eventId + stepName + inputVersion`を冪等性scopeにする

## 9. 楽観的並行制御

- 更新可能aggregateは0始まりの`revision`を持つ
- UPDATEは`WHERE id = ? AND revision = ?`とし、成功行数が1以外なら`409 REVISION_CONFLICT`とする
- 更新後は`revision = revision + 1`とする
- Snapshot、Revision、Correction eventはappend-onlyとし、UPDATEしない
- 古いWorkflowはaggregateの`active_generation`と異なる場合`superseded`で終了する

## 10. Cursor

- cursorはBase64URLのopaque tokenとする
- 中身は`{"v":1,"sort":"...","id":"...","filterHash":"..."}`のcanonical JSONとHMAC signatureとする
- 既定page sizeは50、最大200とする
- cursorと異なるfilterの組合せは`400 INVALID_CURSOR`とする
- sort keyは安定した`created_at, id`または各一覧専用キーとする

## 11. 監査・ログ

- 構造化ログは`timestamp, level, event, requestId, userIdHash, entityType, entityId, durationMs, outcome`を基本とする
- access key、session token、CSRF token、cookie、LLM API key、自由記述、引用原文、LLM payloadをログへ出力しない
- `userIdHash`は環境別pepperでHMACした追跡用値とする
- 監査イベントは認証、credential変更、consent変更、export、削除、運用者の容量profile変更を対象とする
- auditの`metadata_json`にsecretまたは機密原文を入れない

## 12. 共通enum

```typescript
type Visibility = "private" | "unlisted" | "public";
type ReviewDecision = "confirm" | "correct" | "reject" | "conditional";
type AssertionStatus = "proposed" | "confirmed" | "corrected" | "rejected" | "superseded";
type JobStatus =
  | "queued"
  | "running"
  | "waiting_for_user"
  | "retrying"
  | "succeeded"
  | "failed"
  | "superseded"
  | "cancelled";
type Explicitness = "user_explicit" | "user_confirmed" | "inferred" | "model_knowledge";
type Polarity = "positive" | "negative" | "mixed";
```

enumの追加は後方互換とする。削除・改名はAPI major versionまたはmappingを必要とする。

## 13. 環境構成

| 変数 | 秘密 | 用途 |
|---|---:|---|
| `ENVIRONMENT` | No | `local` / `preview` / `production` |
| `APP_ORIGIN` | No | Origin検証 |
| `AUTH_PEPPER` | Yes | credential、CSRF、rate limit、cursor HMAC |
| `TURNSTILE_SECRET` | Yes | Turnstile Siteverify |
| `TURNSTILE_SITE_KEY` | No | browser widget |
| `LLM_PROVIDER` | No | `openai` / `workers_ai` / `replay` / `fake`。composition rootでProvider Adapterを選択。local手動開発の既定は`workers_ai` |
| `LLM_MODEL` | No | 選択Providerの構造化抽出・生成model ID |
| `LLM_FALLBACK_PROVIDER` | No | 空または`openai` / `workers_ai`。自動fallbackを許可する場合のみ指定 |
| `LLM_FALLBACK_MODEL` | No | fallback Provider用model ID。fallback指定時は必須 |
| `OPENAI_FLEX_ENABLED` | No | `true`のときだけOpenAI Responsesへ`service_tier: "flex"`を送る。既定`false` |
| `OPENAI_API_KEY` | Yes | OpenAIをLLMまたはEmbeddingで利用する場合のWorker secret。browserへ公開しない |
| `AI_GATEWAY_ACCOUNT_ID` | Yes | OpenAI Provider Native endpointを組み立てるCloudflare account ID |
| `AI_GATEWAY_GATEWAY_ID` | No | OpenAIとWorkers AIが共通利用するGateway ID |
| `AI_GATEWAY_TOKEN` | Yes | 認証済みGatewayへ送る`AI Gateway Run`権限付きtoken |
| `EMBEDDING_PROVIDER` | No | `openai` / `workers_ai` / `fake`。LLM Providerと独立して選択。local手動開発の既定は`workers_ai` |
| `EMBEDDING_MODEL` | No | 選択Embedding Providerのmodel ID |
| `EMBEDDING_DIMENSIONS` | No | Adapterが検証する返却vectorの期待次元数 |
| `SESSION_DAYS` | No | 既定30 |
| `SESSION_RENEWAL_DAYS` | No | 既定7 |
| `ANALYSIS_DAILY_QUOTA` | No | ユーザー単位の日次解析上限 |
| `GENERATION_DAILY_QUOTA` | No | ユーザー単位の日次生成上限 |
| `EXPORT_DAILY_QUOTA` | No | ユーザー単位の日次export上限 |

D1、R2、Workflows、AIはWrangler bindingで注入する。binding名はDD-01で定義する。live Providerを指定して`AI_GATEWAY_GATEWAY_ID`がない、`workers_ai`を指定して`AI` bindingがない、または`openai`を指定して`OPENAI_API_KEY`、`AI_GATEWAY_ACCOUNT_ID`、`AI_GATEWAY_TOKEN`のいずれかがない構成はProvider factory生成時に失敗させる。未知のDataStore Strategy／Provider設定もfail-fastとする。

`local-manual`と`local-test/CI`はどちらも`ENVIRONMENT=local`の実行profileである。`local-manual`構成は`LLM_PROVIDER=workers_ai`と`EMBEDDING_PROVIDER=workers_ai`を明示設定する。OpenAIのローカル動作確認は一時的なProvider上書きとし、標準構成にはしない。`local-test`/CI構成はLLMを`replay`または`fake`、Embeddingを`fake`で上書きする。未設定値を実行コンテキストから推測せず、Wrangler/Vitest/Playwrightの各構成で明示する。
