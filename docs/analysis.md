# 分析・レビュー・生成の現行仕様

フィクション上の好みを、現実の人格・信条・加害意図へ読み替えません。悪、非道徳、善への無関心、ヴィラン、端役、改心しない人物、一場面の状態も入力として扱います。分析・集計ルールとプロンプト本文の正本は実装です。この文書は処理の境界と不変条件を説明します。

## 登録から確認まで

既成、既成（カスタム）、オリジナルの3方式を扱います。既成のidentity候補は所有者内で照合し、再利用または新規作成を明示します。ユーザーの基本情報、参考資料、解釈、好みの理由、条件を分離します。任意入力の補助は [entry-input](../shared/entry-input.ts)、外部入力と正規化後の型は [entries契約](../shared/contracts/entries.ts)です。

既成キャラクターの公開資料検索と、オリジナルのユーザー入力からキャラクター理解を作成します。カスタム登録では基本像と対象像を分け、改変差分の理由・範囲・根拠を保持します。理解を確認した後に好み分析へ進みます。好みが十分に書かれていない場合、キャラクターの特徴だけからユーザーの好みを確定しません。追加質問・仮説選択も確認フローを通します。

通常版のキャラクター像は監査後に7項目の充足を検査します。各項目には具体的な内容、またはその項目を指す不明理由が必要です。不足があれば一度補完して再監査し、なお7項目すべてが空、または説明のない欠落が残る場合は解析エラーとして停止します。一部だけ不明な場合は理由を表示用の要約に記録し、人物の属性としては追加しません。監査では、公開資料に記述がないという理由だけでモデル知識を一律に削除しません。通常は生成・監査の2回、不足時は補完・再監査の2回が追加されます（各呼び出しの形式修復は別）。[充足検査](../worker/features/analysis/understanding-quality.ts)と[生成・監査処理](../worker/features/analysis/llm-understanding.ts)が正本です。保存済みの空欄は自動修復せず、修正後の再分析で新しい結果を作成します。

通常版の独立監査では、7項目を「具体的な人物描写」「分類名のみ」「出所・解釈の注記のみ」「不明」に分け、改訂後の要約・属性への0始まりの参照番号と理由を返します。構造・参照はコードで検査します。内容のある項目が1つ以下、または具体的描写のある項目が2つ未満なら、既存の補完・再監査を一度だけ実施します。これは創作して埋めるノルマではありません。補完後も部分的な人物像なら、不足理由を表示して確認・好み分析へ進めます。全空・不明理由のない欠落の停止条件は維持します。通常2回、不足時4回で、形式修復は既存の扱いです。dark版の独立理解処理にはこの判定を追加しません。

判定方針 `understanding-information/v1.0.0`、項目別の判定・件数・補完有無・理由は出典評価JSONへ保存し、レビューAPIの基本像・対象像に任意項目 `informationQuality` として返します。`limited`は不足、`not_flagged`は今回の不足基準に該当しなかったことを意味し、事実の正しさや引用の支持を保証しません。旧記録の項目欠落は未評価です。表示は解析時点の記録であり、手動編集では再採点せず、再分析で新しい判定を作ります。エクスポートにも出典評価JSONを保持します。判定は好み分析の入力資料から除き、属性・証拠・信頼度・集計重みへ変換しません。

[固定ケース](../tests/fixtures/sparse-understanding.json)には初回S02の7例・訂正後D10・対照D03の凍結出力と人が定めた判定を収録しています。不明理由の項目別補足と入力スキーマへの変換はテスト補助で行います。固定Providerは保存・続行を検証するもので、実モデルの意味監査精度を実証しません。既存データの自動修復・実API再評価・DBマイグレーションは行いません。

dark版は独立した語彙・反応経路、対象範囲判定、基準状態、変容差分を持ちます。強制された行動と本人の意思、キャラクターへの好意と行為への賛同を分けます。対象範囲に確認が必要な場合は続行・中止の判断を要求します。

## 根拠とレビュー

理解・好み・価値スタンス・改変差分を別の記録として保存し、引用、入力JSON Pointer、出典、検証状態を紐付けます。自由語、統制属性、反応経路、肯定・否定・混合の極性を混同しません。レビューでは確認、訂正、追加、却下を行い、更新対象の所有者・ドメイン・世代を検証します。

外部出典は収集済み資料とProviderの検索出典・引用注釈だけから台帳を作り、`external:<正規化URLのSHA-256>` を既存の `sourceRef` で参照します。台帳は生成・監査・補完で共有し、各試行の出典を保持します。従来のURLは表記正規化後の一致だけを受け付け、編集距離による近似や壊れたpercent符号列の推測は行いません。出典の所在を確認することと、引用が主張を意味的に裏付けることは別です。

照合不能なURL、未知の出典ID、矛盾する参照は根拠単位の `invalid` とし、登録全体を停止させません。無効な根拠しか持たない主張は支持度0でレビューへ残し、一括確認しても後続の理解・要約やプロフィール集計には採用しません。内容を修正保存すると、既存のユーザー確認文の根拠を通じて採用できます。有効・無効の根拠が混在する場合は有効な根拠を維持し、集計の証拠数・品質には無効な根拠を加算しません。

未解決理由・元の参照・対象主張・モデル実行IDを、理解の出典評価JSONと好み分析の品質情報JSONへ保存します。レビューAPIの `understanding`、`baseUnderstanding`、`preferenceAnalysis` には任意項目 `citationIssues` を返し、旧記録では空配列です。通常ログには理由別件数と実行IDのみを出し、モデル応答全文の保存は増やしません。照合方針 `external-id/v1.1.0` はモデル実行設定と生成済みプロンプトmanifestに記録します。v1.1.0は指示本文の処理仕様化であり、参照照合アルゴリズムは変更しません。引用修復用のLLM呼出、DBマイグレーション、過去の登録の自動再解析は追加しません。既存プロフィールは保持され、次の集計から無効根拠の除外を適用します。

訂正・削除された根拠や候補を現行結果へ混入させません。保存と更新の一括処理はD1 batchで原子的に行います。[レビュー実装](../worker/features/entries)と[出典検証](../worker/platform/provenance)を参照してください。

## 手動訂正・追加の根拠

好み・価値態度の内容訂正と追加は、保存した項目を言い換えずに列記した「ユーザー確認文」を作ります。通常版・dark版の共通処理で、候補・属性対応・確認資料・根拠・旧候補の置換を同じD1 batchへ保存します。batch内でも所有者・ドメイン・現行世代・レビュー状態と置換元を検証し、再送や競合更新が重複・部分保存を残さないようにします。

確認資料は `source_type=user_text`、根拠は `evidence_origin=review`、`support_type=supports`、`verification_status=verified_quote` です。本文・ハッシュ・参照位置の一致は、保存した本人申告に対する検証であり、作品設定や外部出典の正しさを示しません。人物理解の資料集合には追加しません。資料メタデータに操作・置換元ID・保存項目・条件・方針 `preference-confirmation/v1.0.0` を保存します。

更新では条件・例外を保持し、旧候補と旧引用は訂正履歴へ残します。新しい主張の支持根拠は新しい確認文1件とし、旧引用をコピーしません。追加操作の説明を適用条件へ混入させません。反応経路だけの変更は従来の根拠・確信度・明示性を保持し、一括確認と同様、無効根拠を有効化しません。

有効な本人申告の根拠品質は1.0とし、既存の強度・`user_confirmed` 係数0.95・偏り補正・分類閾値は維持します。強度0.8・1人物・1作品なら、支持度0.76、プロフィール信頼度0.54055となり、分類は「安定傾向」にはなりません。反復訂正・経路変更・再送で根拠数は増えません。レビューAPIの任意項目 `evidenceOrigin` で確認文を区別し、エクスポートの嗜好候補には `originalLabel` を含めます。

今後の内容訂正・追加から適用します。既存候補の根拠を自動補修せず、元の評価記録を保持します。DBマイグレーション・追加LLM呼出・実API再評価は行いません。[固定fixture](../tests/fixtures/manual-preference-corrections.json) と [保存・集計テスト](../tests/manual-preference-review.test.ts) で今回の7操作と履歴・競合・重みを検証します。

## 否定・対象人物・条件の保持

好みの生成・既存の独立監査（`preference/v3.1.0`）では、原文の「誰が誰に何をする／どの状態になることへの評価か」を、元表現・極性・条件・要約と照合します。否定語を機械的に除去せず、C11の「支配する描写が苦手」と「支配されない関係が苦手」の反転、C12の一方の人物からもう一方への働きかけの逆転を監査対象にします。人物の物語上の時期は `narrativePhases`、ユーザーが好んだ時期は `conditions`、除外条件は `exceptions` に保持します。

対象や極性の意味が監査でも確定できない候補は出力から外し、入力に明示された内容を要約、未確定理由と質問を `uncertainties` に残します。反応経路だけが不明な具体的な好みは、従来どおり `responseChannel=null` で保持します。意味の誤りを引用検証の `invalid` に変換する処理や、追加LLM呼出・正規表現による意味修復は導入しません。

レビューAPIは `originalLabel`・`attributeLabel`・`context`、価値態度には `originalTargetRef`・`scope` を任意項目として追加しています。元表現と標準属性名を併記し、対象人物・関係・時期・条件・例外を通常版とdark版で共通表示します。未知の価値態度キーは推測で翻訳せず、保存済みの関係名と対象範囲を表示し、説明がない場合は「対象未確認」とします。

プロフィールでは条件ごとの候補と正負の支持を表示します。価値態度は対象と範囲ごとに分けます。グラフの接続、スナップショット、生成briefにも元表現と条件を保持し、生成・検証プロンプト（`v2.3.0`）へ引き継ぎます。集計の重み計算は変更しません。旧レコードの追加表示項目は省略可能で、保存済みプロフィール・評価記録は保持します。DBマイグレーションや過去データの自動再解析は行わず、新しいプロフィールの元表現は通常の次回集計から保存します。

[固定fixture](../tests/fixtures/preference-semantics.json) は今回の8ケースの入力・観測結果と、人が定めた期待出力を収録しています。固定Providerのテストは生成・監査・レビュー・集計・生成briefの伝達と追加呼出がないことを検証します。実モデルの意味解釈の改善を実証するものではありません。実APIでの再評価は元の評価と別結果として実施します。

## 集計とグラフ

確認済みの根拠を決定論的に集計し、同一キャラクター・同一作品への偏りを補正します。善悪や物語上の役割を集計上の優劣の係数にしません。プロフィールとグラフは同じ世代へ原子的に切り替えます。現在のアルゴリズムは `profile/v1.2.0-domain-aware`。非対応の保存形式を黙って現行形式として読み替えません。[集計実装](../worker/features/profile/projection.ts)が計算式の正本です。

## 生成と評価

生成には固定した `profileSnapshotId` と、使用・禁止する項目を要求します。条件、反応経路、生成モード、目的、世界観などからbriefを作り、候補生成、結果スキーマ検証、制約検査、類似性検査、保存を順に行います。プロンプト・LLM実行・決定論的検査・Fake出力は別モジュールです。

候補の比較・採用は生成要求単位です。履歴は要求IDごとに候補を一度集約し、既存の履歴順と候補順を保持します。生成だけでは好みプロフィールを更新しません。ユーザーが候補の具体的な設定を評価し、確認した評価を反映します。

## ジョブとデータ保全

ジョブは作成時のモデル・推論量・メンバーシップ割当を保持し、続行・再試行にも同じ割当を使います。所有者・ドメインの分離、世代確認、lease、冪等キー、quota予約、Outboxの重複配送制御を維持します。再試行できる失敗だけを再実行し、遅れて完了した古い実行で新しい成功結果を上書きしません。

DBのテーブル・属性IDは [migrations](../database/migrations) に保持します。ユーザーのエクスポートは非公開R2へ非同期生成し、ダウンロード時は所有者を確認します。アカウント削除・履歴削除はそれぞれのユースケースを通します。

## プロンプトの適用範囲

固定指示は「共通ルール＋該当版のルール＋処理目的のルール」で組み立てます。出力SchemaとLLM呼び出し回数はこの分離によって変更しません。

| 処理 | 適用する指示 |
| --- | --- |
| 好みの抽出・監査 | 共通の命名・根拠・条件の保持と、通常版またはdark版の属性・反応経路。通常版の意味監査は通常版の監査時だけ追加。 |
| 仮説提案 | 共通の命名と該当版の属性範囲。確認済み人物理解から未確認の好みを提案し、説明・理由・範囲に分ける。抽出用evidenceや出典台帳、監査用項目は要求しない。 |
| 通常版の人物理解 | 人物像の構成と出所の区別。監査時だけ情報量評価と人物理解用の意味監査を追加。好み専用の出力項目は要求しない。 |
| dark版の人物理解 | 対象判定・変化前の基本像・対象状態・独立監査を分ける。一般属性の抑制は対象状態に適用し、比較用の基本像へ持ち込まない。 |
| キャラクター生成・検査 | 条件・反応・価値態度の保持は共有。ダーク文脈とPointer例は版別にし、選択済みの辞書外ダーク属性も扱う。 |

仮説は専用の最大6件のプレビュー経路へ統一します。現在の受付処理が保存する元分析IDのない仮説要求はエラーとして扱い、旧来の「最大3件・確信度0.35以下」で好み分析へ流す経路は使いません。既存データの書き換えや自動再分析は行いません。
