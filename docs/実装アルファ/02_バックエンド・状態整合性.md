# バックエンド・状態整合性

## 1. Workflow と job の世代フェンスが必要

### 現状

分析 Workflow は job 作成時の `input_generation` を持っていますが、処理本体の `loadEntry()` は「その時点の active revision」を読みます（`worker/services/analysis.ts:117-155`）。開始・成功・失敗の更新にも、期待する generation や期待する現在 status の条件がありません（同 `:487-698`）。

そのため、次の競合が成立します。

```text
job A (generation 1) を作成
  -> 再分析で revision/generation 2 と job B を作成
  -> 遅れて job A が開始
  -> job A が generation 2 の入力を読み、古い job ID で結果と status を更新
```

さらに理解確認では、Entry に属する job を generation/status で絞らず一括で `queued` にしています（`worker/services/entries.ts:613-615`）。API 側の「最新 job」も `created_at DESC LIMIT 1` であり、同時刻や generation の意味を直接表していません（`worker/index.ts:330-334`）。

### 推奨設計

- job claim を `UPDATE ... WHERE id=? AND status='queued' AND input_generation=? RETURNING ...` のような比較交換にする。
- 各 Workflow 開始時に `input_revision_id`、`input_generation`、現在 active revision を照合する。
- すべての結果保存・status 遷移に期待 generation/status を含める。
- supersede 時は古い job を明示的に終端状態へ移し、その後の書込を拒否する。
- Entry、revision、analysis run、job の組を1つの実行コンテキストとして渡し、処理途中で「最新」を再検索しない。
- 競合は例外ではなく `superseded` として観測可能にし、利用者向けには新しい job を返す。

### 必須テスト

1. generation 1 を停止させたまま generation 2 を完了し、その後 generation 1 を再開しても状態・run・profile が変化しない。
2. 同一 Workflow instance の重複配送で LLM 呼び出しと result insert が1回だけになる。
3. 成功済み job に遅い失敗ハンドラが到着しても `failed` へ戻らない。

## 2. run と entry の関連を確認 API が保証していない

`activateAnalysisAndRebuild()` は、渡された `analysisRunId` の assertion を owner 条件だけで確認し、別に渡された `entryId` を active にします（`worker/services/analysis.ts:930-968`）。run がその Entry の active revision に属するかを検証しません。

同じ利用者が所有する Entry A と Analysis Run B を組み合わせると、B の assertion を confirmed にしながら A を active にできます。更新件数ゼロの検査もないため、不正な組合せを成功扱いにし得ます。

推奨する SQL 境界は次のとおりです。

1. `analysis_runs -> entry_revisions -> entries` を join する。
2. run が `analysis_review` の entry の current revision に属することを確認する。
3. run の status、entry の status、revision generation を条件付き更新する。
4. assertion 確認と entry 有効化を同一 batch/transaction にする。
5. affected rows が期待数でなければ 409 を返す。

API schema でも `entryId` と `analysisRunId` の二重指定を避け、`POST /analysis-runs/:runId/confirm` のように run から Entry を一意に解決すると、組合せ不整合そのものを作りにくくできます。

## 3. DB commit と Workflow 起動の間に欠落窓がある

Entry 作成、再分析、生成は、先に D1 に job を作り、その後 Binding の `.create()` を呼びます（`worker/index.ts:276-291`, `:301-316`, `:388-403`）。起動に失敗すると HTTP は 500 でも queued job は残ります。同じ idempotency key で再送すると「既存結果の replay」となり、Workflow は再起動されません。

理解確認も先に DB 状態を変更してから profile Workflow を起動するため、起動失敗後は「確認済みだが profile 未反映」になります。

### 推奨

最も扱いやすいのは transactional outbox です。

```text
API transaction
  ├─ source-of-truth/status 更新
  └─ outbox に dispatch 要求を insert

dispatcher
  ├─ instance ID を決定的に作成
  ├─ Workflow create（重複は同一扱い）
  └─ outbox を dispatched に更新
```

短期対策として replay 時に queued かつ `workflow_instance_id IS NULL` の job を再 dispatch する方法もあります。ただし API request と起動の間の crash は残るので、最終的には outbox と定期 repair が必要です。

## 4. Workflow の retry 設定が実質無効

Workflow 側は `step.do()` に retry を設定しています（`worker/workflows.ts:7-25`）。一方、分析・プロファイル・生成サービスは広い `catch` で例外を DB の failed 状態へ変換し、再送出しません（`worker/services/analysis.ts:691-697`, `:918-925`, `worker/services/generation.ts:531-538`）。Workflow ランタイムから見ると step は正常終了したため、ネットワーク断や 429/5xx でも自動 retry が働きません。

次のエラー分類を共通化すべきです。

| 分類 | 例 | 動作 |
|---|---|---|
| retryable | 429、LLM 5xx、接続断、D1 一時障害 | attempt を記録し例外を再送出。上限後に failed。 |
| permanent | schema 不正、参照 ID 不整合、ポリシー違反 | 直ちに failed。利用者向け理由を安定した code で保存。 |
| superseded | 世代不一致、既に別 job が成功 | 副作用なしで終端。失敗率には算入しない。 |
| operator action | 設定欠落、dimension 不整合 | readiness を落とし、ジョブを無制限 retry しない。 |

`job_attempts` が既に DDL にあるため、attempt、provider request ID、開始/終了時刻、分類、次回実行時刻をそこへ接続できます。

## 5. profile と graph は修復可能な派生データにする

確認処理は Entry を active にした後で `rebuildProfile()` を呼びます（`worker/services/analysis.ts:960-968`）。アーカイブも先に source 状態を変えてから rebuild します（`worker/storage/strategy.ts:79-88`）。profile は graph より先に current 化されます（`worker/services/profile.ts:460-463`）。

この順序では次が起こります。

- Entry は active だが profile が古い。
- profile は新しいが graph は古い。
- 同時 rebuild が同じ `MAX(generation)+1` を選び、一意制約競合になる。
- 失敗後に利用者操作を繰り返しても、状態条件のため再構築要求を作れない。

source-of-truth を正しく commit した後、profile/graph は再計算可能な projection として扱うのが適切です。

- 利用者単位の desired generation を増やす。
- rebuild request を coalesce し、同一利用者では1 worker だけが claim する。
- profile と graph の生成物を同じ source watermark に結び付ける。
- 両方の構築完了後に current pointer を原子的に切り替えるか、それぞれの freshness を API に返す。
- `GET /profile` は `source_generation` と `built_generation`、stale/rebuilding を返す。
- 定期 repair が active source と projection watermark の差を検知する。

## 6. Generation は at-least-once を前提にする

`processGeneration()` は status による claim なしに running へ更新し、毎回新しい brief/result を insert します（`worker/services/generation.ts:205-331`, `:436-540`）。重複実行の一方が成功した後、もう一方の catch が job を failed に戻すことも可能です。また、共通 retry API は Character Analysis 用関数だけを呼ぶため、generation job の retry 導線がありません（`worker/index.ts:420-437`）。

推奨事項:

- `generation_job_id` に対する brief/result の一意性を DB で保証する。
- queued -> running を条件付き claim し、running/succeeded は重複実行しない。
- success/failure update に期待 status と attempt を含める。
- retry は新 attempt として入力 snapshot を固定し、同じ結果を上書きしない。
- analysis job と generation job の retry policy/API を型で分離する。
- UI から retryable/permanent の違いを確認できるようにする。

## 7. quota と idempotency の順序

Entry、再分析、生成の各 route は quota を先に消費してから idempotency replay を確認します（`worker/index.ts:276-283`, `:301-309`, `:388-395`）。通信再送でも quota が減り、同じ key に異なる payload を送った 409 の場合にも quota を先に消費します。逆に手動 retry は quota 検査を通らず、1つの「分析」は複数回の LLM 呼び出しを行います。

改善案:

1. idempotency key と payload hash を最初に検索する。
2. 同一 replay は保存済みレスポンスを返し quota 非消費。
3. 新規要求だけを、quota reservation・job 作成・idempotency 記録と同一 transaction にする。
4. LLM call 数、token、同時数、日次 job 数を別メトリクスとして持つ。
5. retry は自動 retry、利用者 retry、設定修正後 retry で課金・quota 方針を分ける。

## 8. D1 の bind parameter 上限

生成入力の ownership 検証は snapshot ID と selected/prohibited ID を1本の `IN (...)` query に bind します（`worker/services/generation.ts:394-402`）。入力 schema は selected と prohibited を各100件まで許すため、最大201 parameter です。

Cloudflare D1 の現在の上限は1 query あたり100 bound parameters で、batch 内でも各 query に個別適用されます（[D1 Limits](https://developers.cloudflare.com/d1/platform/limits/)）。ローカル SQLite の単体テストではこの差が表面化しません。

対処は次のいずれかです。

- selected + prohibited の合計を、snapshot ID 等を含めて100未満になるよう API schema で制限する。
- ID を安全な件数へ chunk し、全件の存在・owner・snapshot を照合する。
- 一時表/永続 selection table に保存して join する。

単に配列ごと100件を許可するテストではなく、99/100/101 parameter の境界を D1 相当環境で確認してください。

## 9. その他の整合性改善

- `created_at DESC` だけで最新を選ばず、generation と一意な順序キーを使う。
- 状態遷移を route/service ごとの文字列 UPDATE ではなく、共通 state machine と許可遷移表へ寄せる。
- `error_message` の自由文と利用者表示用 `error_code`、内部診断を分離する。
- pending user、session、rate limit、idempotency、期限切れ outbox を retention policy に基づき回収する。
- `APP_ORIGIN` 等の本番 placeholder/空文字を起動時に拒否し、request origin への暗黙 fallback を本番では使わない。
