## 2. E2E を hermetic にする

`playwright.config.ts` は `reuseExistingServer: true` です。今回 5173 番で既に通常開発サーバーが動いていたため、Playwright が E2E 用 `offline` server を起動せず、そのサーバーへ接続しました。通常構成では Turnstile 検証が必要だったため、登録が400になり全4件が失敗しました。

専用 port と一時的な offline env に分離すると、主要画面の2件は成功しました。残る失敗は次の通りです。

- `getByLabel(/作品名/)` が作品名 input と説明を持つ reference textarea の2つに一致。
- security spec が Origin を `http://localhost:5173` に固定し、専用 port と不一致。

### 推奨構成

- E2E は毎回専用 port を確保し、既存サーバーを再利用しない。
- 専用 D1 database/path、専用 pepper、`LLM_PROVIDER=fake`、Turnstile 無効を test config に固定する。
- server 起動後、health/diagnostics の実効 provider・mode・DB namespace を assert する。
- テストごとに unique user を作り、終了時に専用 DB 全体を破棄する。
- Origin/baseURL は同じ config から生成し、文字列を spec に埋め込まない。
- accessible selector は exact name または role/name の一意性を確認する。
- `env.offline` で Workflow binding が継承されない警告を解消し、fallback の `waitUntil` 経路を意図的にテストする場合は別 suite にする。

`reuseExistingServer` を local developer convenience として残すなら、接続先の build/config fingerprint が違う場合は即失敗させます。

## 3. 追加すべき回帰テスト

### P0/P1 の状態競合

- 古い analysis Workflow と新しい generation の交差。
- Workflow start 前 crash と idempotent replay。
- duplicate delivery、遅い failure、同時 profile rebuild。
- run/entry を別々に指定した confirm の拒否。
- active commit 後に graph build が失敗し、その後 repair で一致する。
- generation の retry と success immutability。
- 同じ idempotency key の同一/異なる payload、quota 非重複消費。

### 認証/API

- Origin missing/null/wrong scheme/wrong port。
- key rotation の pending/confirm/cancel/expiry。
- pending username の expiry と再利用。
- 所有者外の全 resource ID。親を自分、子を他人にした混合 ID も含む。
- validation error、413、404、409、429、LLM error の共通 envelope。
- export manifest と削除対象の対称性。

### LLM fixture

- provider を呼ばない固定 raw response fixture。
- valid、malformed JSON、schema mismatch、repair success/failure。
- citation/pointer/quote の正当・改ざん・offset 不一致。
- 否定、皮肉、矛盾、情報不足、同名別作品、ネタバレ scope。
- 現実価値観と創作嗜好、no-redemption 等の protected meaning。
- prompt/schema version ごとの golden diff。完全一致ではなく許容する意味指標も定義する。

### ブラウザ/アクセシビリティ

- Chromium desktop だけでなく、主要導線を Firefox/WebKit と mobile viewport で smoke。
- keyboard only、focus order、dialog focus trap、reduced motion、contrast。
- graph の表形式代替と screen reader name。

## 4. 契約検査は存在するが、同じ契約を比較していない

`scripts/check-schemas.mjs` は JSON の parse、local `$ref`、response channel と DDL の一部整合を確認します。`scripts/check-ddl.mjs` は代表10 table の存在、空 DB に対する foreign key check、ontology が80件以上であることを確認します。いずれも有用ですが、次の差は検出しません。

- Hono route と OpenAPI path/method の差。
- request/response Zod と OpenAPI schema の差。
- `shared/schemas.ts` と `docs/詳細設計/schemas/*.schema.json` の maxLength/maxItems/enum 差。
- service の SQL column と migration の互換性。
- migration 後の実データに対する foreign key/orphan。
- D1 固有の parameter/query/transaction 制限。

実例として、generated character の relationship/speech/narrative/arc の一部は文書 JSON Schema に max length がありますが、実行時 Zod には同じ上限がありません（`shared/schemas.ts:302` 以降）。配列上限も文書と実装で異なる箇所があります。

### 推奨する single source of truth

1. 現行 route を表す as-built OpenAPI を用意する。
2. OpenAPI から client/schema を生成するか、Zod から OpenAPI を生成する。
3. LLM output JSON Schema は同じ canonical schema から生成する。
4. hand-written DB 制約だけは migration test で補う。
5. CI で生成差分が出たら fail し、生成物を commit する。

現在の OpenAPI は目標仕様の細粒度 endpoint を多く含み、実装は集約 endpoint を中心にしています。詳細設計にも差分の説明はありますが、API consumer が「今使える契約」を機械的に判定できません。target と as-built をファイル名・version・公開先で明確に分けてください。

## 5. D1/Workers 固有制約をテストへ入れる

ローカル SQLite が通っても D1 では通らない代表例が bind parameter 上限です。現在の公式制限は1 query 100 parameters で、生成検証は最大201個を bind し得ます（[D1 Limits](https://developers.cloudflare.com/d1/platform/limits/)）。

また Workers は plan ごとに CPU、subrequest、request body 等の制限があります。現行の公式値を deploy target ごとに確認し、profile/graph rebuild の Entry 数・assertion 数・query 数に budget を置いてください（[Workers Limits](https://developers.cloudflare.com/workers/platform/limits/)）。

推奨する platform test:

- preview/remote D1 で 99/100/101 bind parameter。
- migration を空 DB と1世代前 fixture の双方へ適用。
- 最大 Entry/assertion/profile/graph を持つ fixture で query count/CPU/response size を測定。
- D1 busy、一時失敗、partial batch failure の fault injection。
- Workflow duplicate/retry/delay を模した integration test。
- production と同じ compatibility date/bindings を使う pre-deploy smoke。

## 6. CI gate

リポジトリには現時点で CI workflow がありません。最低限、PR ごとに次を実行します。

```text
npm ci
  -> check + typecheck
  -> unit + coverage threshold
  -> contract generation/diff
  -> migration test
  -> build + secret artifact scan + bundle budget
  -> hermetic offline E2E
```

main/release では preview Cloudflare への deploy、remote D1 smoke、OpenAI/Workers AI の少数 canary を追加します。外部 LLM test は quota と揺らぎがあるため、通常 PR の必須 gate は fixture/fake にし、canary failure は model/provider 変更の判断材料として別管理するのが適切です。

coverage は全体の数字だけでなく、状態遷移、ownership、quota、idempotency、provenance verifier を高い branch threshold にします。

## 7. 依存管理

`package.json` のほぼ全依存が `latest` です。lockfile がある間は一定ですが、新規解決や意図しない lock 更新で major change が混ざりやすくなります。

- production/dev dependencies を reviewed range または exact version にする。
- CI と deploy は `npm ci`。
- update PR を dependency/group ごとに分ける。
- Wrangler、Workers types、Hono、Zod、React、Vite/Playwright は変更影響が異なるため一括更新しない。
- `npm audit` 0件は維持しつつ、audit だけを更新理由にしない。

今回の `npm outdated` では patch/minor と jsdom の major 更新候補がありましたが、本監査では更新していません。互換テストを伴う別変更にするのが安全です。

## 8. 運用ジョブと未接続 schema

DDL には `job_attempts`、outbox/capacity、consents、feedback、similarity、profile patterns 等の将来用構造がありますが、多くは現在の処理へ接続されていません。schema があるだけで機能・監視があるように読めるため、表ごとに次を明示してください。

| 状態 | 意味 |
|---|---|
| active | write/read/retention/monitoring が実装済み |
| shadow | write するが製品判断には未使用 |
| reserved | 将来 migration の予約、現行コードは依存しない |
| deprecated | 新規 write なし、削除予定 |

必要な定期処理:

- expired pending users/activation secrets の削除。
- expired sessions、rate-limit buckets、idempotency records の回収。
- stuck queued/running job と未 dispatch outbox の repair。
- profile/graph watermark の差分 repair。
- audit/model run/source document の retention と利用者削除への追随。

メトリクスは job 成功率だけでなく、queue age、retry/repair 数、superseded 数、profile staleness、provider fallback、schema repair、evidence verification failure を持つと、品質低下を早く検知できます。

## 9. 文書の鮮度

既存の完了定義には単体テスト6ファイル・27件、E2E 3件等、現状と違う値があります。README の local default provider と `wrangler.jsonc` の実設定も一致しない箇所があります。

- test count、schema count、bundle size、provider/model は build/release report から自動生成する。
- 「目標仕様」「アルファ実装済み」「将来予定」を同じチェックリストで混在させない。
- environment matrix は `wrangler.jsonc` から生成し、secret 名だけを表示する。
- pricing/limit は取得日と公式 URL を付ける。Workflows の現行制限を参照する場合は [Workflows Limits](https://developers.cloudflare.com/workflows/reference/limits/) を正とする。
