# 改善ロードマップ

> 2026-08-30更新: Phase 0〜4のうちP0〜P2対象を実装済みです。credential ceremonyの`AUTH-01`は利用者指定により受容し、P3項目は対象外です。最終状態は[00_対応状況.md](00_対応状況.md)を参照してください。以下は実装順を決めた当時のロードマップとして保持します。

個別指摘を順番に直すより、整合性境界ごとにまとめる方が安全です。以下は依存関係を考慮した推奨順です。期間見積りではなく、完了判定可能な変更単位を示します。

## Phase 0: 表示と回復不能操作を止血する

### 0-A. 説明文を実装へ合わせる

- 設定画面の LLM、外部検索、モデル知識に関する誤った説明を修正する。
- Landing の「原文から追跡」「評価で育つ」は現行能力に限定する。
- export を「概要」に改称するか、不足項目を明示する。
- system research を試験機能として表示し、利用有無を利用者が認識できるようにする。

完了条件: デプロイ環境の provider/調査機能/保存範囲と、画面・プライバシー説明・README が一致する。

### 0-B. credential ceremony を安全にする

- 新規アクセスキー dialog を非 dismissible にする。
- 新規登録にある copy/download/保存確認をローテーションにも揃える。
- rotation を pending new key -> confirm -> old key revoke に変更する。
- pending user expiry cleanup と username 再利用を実装する。

完了条件: dialog close、tab close、通信再送、clipboard failure のいずれでも、既存利用者が全 credential を失わない自動テストが通る。

## Phase 1: 非同期状態機械を作り直す

### 1-A. 共通 job state machine

- job に input revision/generation、attempt、workflow instance、terminal reason を持たせる。
- queued -> running -> succeeded/failed/superseded を条件付き更新にする。
- success を後続 failure が上書きできない DB 条件を追加する。
- retryable/permanent/superseded/config error を共通分類する。

### 1-B. outbox と dispatcher

- Entry 作成、再分析、確認、アーカイブ、生成と dispatch request を同一 transaction にする。
- 決定的 instance ID と重複 dispatch の無害化を実装する。
- queue age と未 dispatch を repair する scheduled job を追加する。

### 1-C. projection generation

- profile/graph を source watermark 付き projection にする。
- 同一利用者の rebuild を coalesce/serialize する。
- current pointer を完成後に切り替える。
- stale/rebuilding を API/UI へ返す。

### 1-D. 関連整合性

- confirm は Analysis Run だけを URL key にし、Entry/revision を server で解決する。
- run、revision、Entry、owner、status、generation を1回の整合検査にする。

完了条件: duplicate、delay、out-of-order、start failure、D1 transient failure の fault-injection suite が通り、source と projection の watermark が最終的に一致する。

## Phase 2: provenance と分析単位を修正する

### 2-A. source model

- 入力フィールド、利用者資料、system research、hosted search、model knowledge を別 source として表す。
- URL、取得時刻、input pointer、quote/offset、content hash を持つ。
- OpenAI annotation を adapter から永続層まで通す。

### 2-B. assertion evidence

- LLM output schema に source/pointer/quote/inference を追加する。
- server-side verifier を実装する。
- verified/unverified を分け、UI は検証済みだけを「追跡可能」とする。

### 2-C. identity/work と context

- owner 内 canonical work/identity と Entry revision を分離する。
- merge/split/version override を設ける。
- preference assertion の context を profile condition と generation まで伝播する。

完了条件: すべての confirmed assertion について、根拠なし、検証済み根拠、model knowledge のいずれかが一意に判定できる。同一作品/identity の重複登録テストで設計どおりの割引が働く。

## Phase 3: 契約と品質 gate を一本化する

### 3-A. as-built contract

- 現行 route の OpenAPI を作る。
- Zod/OpenAPI/JSON Schema/client type を同じ定義から生成する。
- target API は別 version/文書へ分離する。
- D1 100 bind parameter を超えない schema/query に変更する。

### 3-B. LLM observability

- repair attempt の idempotency key を分ける。
- prompt hash/version、provider attempt、fallback chain、実効設定、token/latency を保存する。
- environment config を中央検証し、readiness と diagnostics を分離する。

### 3-C. hermetic CI

- `npm ci`、lint/type、unit/coverage、contract diff、migration、build/bundle budget、offline E2E を必須化する。
- E2E は専用 DB/port/env を使う。
- preview D1/Workers smoke を release gate にする。

完了条件: clean clone から単一コマンドで同じ結果を再現し、実装と契約の差、secret artifact、bundle 超過、migration 失敗を CI が検出する。

## Phase 4: 生成品質とプロダクト完成度

- generation coverage の exactly-once、pointer 実在、禁止制約を決定的検証する。
- 意味検査 fixture と利用者 feedback の取り込み方を決める。
- generation retry UI と失敗分類を追加する。
- profile patterns を生成し、dimension/stance/condition の説明を改善する。
- route/graph を lazy load し、graph の表形式代替を追加する。
- full export/import、public visibility、consent/retention を製品方針に沿って完成させる。

完了条件: 代表的な positive/negative/conditional/no-redemption fixture で制約保持を定量評価し、UI から各生成要素の採用・競合・回避根拠を追跡できる。

## 推奨 PR 分割

相互依存はありますが、レビュー可能性のため次の単位を推奨します。

1. 説明文の訂正と credential dialog の暫定止血。
2. job state enum/conditional transition と競合再現テスト。
3. outbox/dispatcher と Workflow retry 分類。
4. profile/graph watermark と repair。
5. confirm API の run-centered 化。
6. provenance schema/source persistence/verifier。
7. canonical work/identity と context aggregation。
8. as-built OpenAPI と schema generation。
9. hermetic E2E/CI/platform boundary tests。
10. generation semantic coverage、UI、性能・アクセシビリティ。

DB migration を含む PR は expand -> backfill -> dual-read/dual-write -> cutover -> contract の段階を分けます。既存 assertion/evidence は真の出典を復元できないため、推測で埋めず `legacy_unverified` として移行するのが安全です。

## アルファ継続・公開判定 gate

### 限定アルファを継続できる条件

- PRIV-01 の説明訂正が完了している。
- credential 紛失リスクを参加者へ明示し、回復手段または非 dismissible UI がある。
- stuck job/profile stale を運用者が検知・手動 repair できる。
- テスト利用者と実データを分離している。

### 一般公開へ進める条件

- P0 がすべて完了。
- REL-03〜REL-06 の fault-injection test が成功。
- evidence verifier が入り、未検証根拠を追跡可能と表示しない。
- canonical identity/work の仕様決定と偏り補正テストが完了。
- hermetic CI と preview smoke が release 必須 gate。
- privacy/export/retention の表示と実装が一致。
- readiness、queue age、fallback、projection staleness を監視できる。

## 実装後の再監査ポイント

- 状態遷移 SQL の全書込に期待 status/generation があるか。
- outbox と source commit が同じ transaction か。
- すべての assertion から source/input/model knowledge へ辿れるか。
- UI 表示が verified/unverified/inferred を取り違えないか。
- duplicate registration が意図した canonical ID を使うか。
- OpenAPI と実 route の自動 diff がゼロか。
- local fake、staging Workers AI、本番 OpenAI/fallback の全環境で同じ論理契約が通るか。
- 利用者削除と export が、新しく追加した source/attempt/outbox/projection を漏らさないか。
