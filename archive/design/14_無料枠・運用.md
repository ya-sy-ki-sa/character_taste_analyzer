# DD-14 現行運用

## 1. 環境分離

local、preview、productionはD1、R2 `EXPORTS`、Workflowを分離する。staging／productionのresource IDはdeploy前に`wrangler.jsonc`のplaceholderを実値へ置き換える。secretはWrangler secretで登録し、repositoryやbuild成果物へ含めない。

`DEPLOYMENT_PROFILE`は使用しない。運用上限は次の明示設定で管理する。

- `ANALYSIS_DAILY_QUOTA`
- `GENERATION_DAILY_QUOTA`
- `EXPORT_DAILY_QUOTA`
- public／user／IP rate limit

## 2. Readiness

非local環境ではD1、`AUTH_PEPPER`、選択したLLM／Embedding Providerのsecretまたはbinding、R2 `EXPORTS`、4 Workflow、`APP_ORIGIN`を検証する。productionではTurnstile secretも必須とする。

現行構成にVectorize bindingはなく、readinessでも要求しない。未知のDataStore Strategy、LLM Provider、Embedding Providerは起動時にfail-fastとする。

## 3. 監視

- `/api/v1/health/live`: processがrequestを処理できること
- `/api/v1/health/ready`: 必須設定とbindingが揃うこと
- Job／attempt: running時間、retry、最終error code
- quota: reservationと日次確定数
- export: queued／running／ready／failed／expired
- projection rebuild: desired generationとbuilt generationの差

logにはaccess key、session token、CSRF token、Entry原文、LLM response本文を出さない。

## 4. Backupと移行

D1のbackupは環境と時刻を明示し、暗号化・アクセス制御された場所に置く。side-by-side移行では新DBへbaselineを適用し、件数、content hash、外部キー、`integrity_check`、login/session、レビュー再開、生成JSONを検証してからbindingを切り替える。

旧DB／backupの削除は切替後の検証完了に限定し、globや広いdirectoryを対象にせず各pathを個別解決する。移行専用scriptとreportは運用完了後に削除する。

## 5. 障害時

- LLM一次障害は、設定済みで異なるProviderのfallbackだけを許可する
- Profile rebuild失敗時はlive projectionを捏造せずfreshnessを`failed`にする
- R2 export失敗はJobを失敗させ、D1正本は維持する
- D1 integrity／FK不整合時はbinding切替を行わない
- account削除ではprivate export objectを削除後、D1所有データを物理削除する
