# 画面・コンポーネント・文言パターン

## 1. 共通の情報設計

世界観の語彙は、ユーザーが行う操作と一対一で対応させる。

| 通常の機能 | 観測装置としての表現 | 主表示に適した文言 |
|---|---|---|
| 分析を始める | 観測開始 | 嗜好を観測する |
| 分析結果 | 観測座標／観測結果 | 観測結果 |
| 保存データ | 観測記録 | 観測記録 |
| フィルター調整 | 焦点／条件調整 | 条件を絞り込む |
| ユーザー | 観測者 | ユーザー名 |
| 認証 | 記録へのアクセス | ログイン |
| 設定 | 装置校正 | 設定 |

比喩は補助層に置き、ボタンとフォームラベルは通常の言葉を優先する。「FOCUS CALIBRATION」だけでフィルターを表すような置換はしない。

## 2. トップ／認証画面

トップ画面の仕事は、初めてのユーザーを登録へ、既存ユーザーをログインへ進めること。**トップ画面には「新規ユーザ作成」と「ログイン」の二つの主要ボタンだけを置き、ユーザー一覧を置かない。**

推奨構成:

- ヘッダー: 「キャラ嗜好ラボ」「嗜好天体観測装置」、任意の装置ID、短い準備状態。
- 操作盤: ラベル「観測をはじめる」、見出し「好きは、観測できる。」、機能が理解できる2–3行の説明。
- 操作: 強調された「新規ユーザ作成」と、抑えた「ログイン」。優先順位はユーザー要件に従う。
- 信頼情報: 「分析内容と生成履歴はログインキーで保護されます」のような事実だけを記載する。
- 観測スコープ: 表情、信念、関係性、葛藤など、サービスが扱う実際の嗜好軸を表示する。

ログインはモーダルまたは既存の認証画面として実装し、少なくとも次を持つ。

- 見出し「観測記録を開く」または明快な「ログイン」
- `ユーザー名`、`autocomplete="username"`
- `ログインキー`、`type="password"`、`autocomplete="current-password"`
- 送信「ログイン」、閉じる操作、Escape、初期フォーカス、エラー表示

新規ユーザ作成は次を持つ。

- 見出し「観測者を登録する」または「新規ユーザ作成」
- `ユーザー名`、`autocomplete="username"`
- `ログインキー`、`type="password"`、`autocomplete="new-password"`
- 送信「新規ユーザ作成」、閉じる操作、入力要件とエラー表示

## 3. 分析画面

- 主役は観測スコープ、レーダー、散布図など、実データを読み取れる一つの可視化にする。
- 条件入力は左の操作盤または下部の制御卓へまとめ、結果と混在させない。
- 軸、凡例、値、選択状態を明示する。色だけで違いを伝えない。
- 生成中は走査線や進捗を使えるが、完了時間を偽らない。キャンセルや再試行が可能なら実装する。
- 結果の要約は「どの特徴が強いか」「どの入力に基づくか」「次に何ができるか」の順で書く。

## 4. 履歴／一覧画面

- 履歴は「観測記録」として、テーブル、ログ、タイムラインなど比較しやすい形で示す。
- 同じ形の大きなカードを繰り返さない。日時、対象、主要傾向、状態、操作を列として揃える。
- ソート、フィルター、ページ送りは実際に動かし、選択状態をテーマの構造色または信号色で明示する。
- 空状態は「観測記録はまだありません。最初の嗜好観測を始めてください」のように、状態と次の操作を明記する。

## 5. プロフィール／設定画面

- 設定は「校正盤」のような密度で、ラベルと入力を明確に整列させる。
- セクション境界は1px線と余白で作り、各フィールドをカード化しない。
- 保存ボタンは一つの明確な主要操作にし、未保存・保存中・保存完了・失敗を表示する。
- 破壊的操作は信号色を常用せず、専用領域と確認手順で区別する。

## 6. コンポーネント契約

### ボタン

- 長方形、角丸0–2px、最小高さ48px。太めのゴシック体を使う。
- Primaryはテーマの`action`面、Secondaryは暗い面＋`structure`または`control-edge`の境界。通常版は赤／真鍮、dark版は青鋼／鈍銀になる。
- 押下で1–2px沈む、信号灯が点灯するなど、機械的な反応を一つ与える。
- Hoverだけに意味を持たせず、`focus-visible` を2px以上の高コントラストな輪で示す。テーマの信号色だけで不足する場合は主要文字色を併用する。
- ピル型、過剰なグロー、複数の競合するPrimaryを避ける。

### 入力

- 暗い単色面、`control-edge`の1px枠、テーマの主要文字色、48px以上の高さ。
- ラベルを常に表示し、placeholderで代用しない。
- エラーは枠色だけでなく文章と関連付ける。ブラウザの自動入力でも文字が読めるよう確認する。

### ダイアログ

- 幅は概ね `min(92vw, 480px)`。筐体の一部を引き出したような平面と境界で作る。
- 背景は十分に暗くするが、モーダル自体と同化させない。
- 見出し、閉じる、フォーム、主要送信の順序を保つ。閉じた後は起動ボタンへフォーカスを戻す。

### ステータスとラベル

- 状態は点灯、短い文言、必要ならアイコンの組み合わせで示す。
- 緑を安易な装飾に使わない。成功、準備完了、警告、エラーの意味をプロジェクト全体で固定する。
- 英字の装置IDは補助情報。日本語の機能名より目立たせない。

## 7. レスポンシブ変換

- 980px前後: 左操作盤を約300px、右校正レールを約52pxへ縮め、スコープをビューポートに収める。
- 720px以下: ヘッダー、操作盤、スコープ、フッターの一列へ変換し、校正レールを省略する。
- モバイルではスコープを小さなカードへ縮小せず、横幅いっぱいに見せ、必要なら円の一部を意図的に切る。
- 430px以下: 二つの認証ボタンを一列へ積む。主要文言、軸名、操作は残し、補助英字や軸説明から省略する。
- 320px幅まで横スクロール、重なり、切れた主要操作を発生させない。

## 8. 文体

- 短く、具体的で、能動態にする。ボタンは実行後の結果と同じ名前にする。
- 詩的な表現は主見出し一つ程度に留める。説明とエラーは平易に書く。
- エラーは謝罪ではなく、問題と直し方を示す。例: 「ログインキーが一致しません。入力を確認して再試行してください。」
- 装飾のためだけの座標、観測番号、計測値を生成しない。
